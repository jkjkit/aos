# Grill

对任意主张、想法、方案进行连续追问的 Skill。**只提问不解答**——目的是把模糊的脑内模型拎出来变成可执行的问题，而不是直接给方案。

## 何时使用

- 用户说「我想做 X」但描述模糊，先 grill 再 design
- 用户问「这个方案好不好」，让 grill 找漏洞再决定是否走 design / research
- 用户做了技术决策但理由没说清
- 团队讨论卡在「我们觉得应该这样」但说不清为什么
- 任何「听起来合理」但没经过压力测试的判断

不要用于：

- 已经清楚的需求（直接 design）
- 用户明确要答案（用 design / research / coding）
- 已经验证过的方案（用 review）

## 流程

### 1. 锚定主题

第一轮：把用户的原始表述复述一遍，确认你理解对了。不要急于追问，先校准。

### 2. 选择追问方向

按优先级挑**当前最值得追问的角度**，每轮只问 1-2 个：

1. **前提质疑**：你默认了什么？那个默认对吗？
2. **证据要求**：你怎么知道的？有没有具体数字 / 例子 / 来源？
3. **反例构造**：什么时候这个判断会反过来？最坏情况是什么？
4. **边界划定**：在什么范围内成立？超出范围会怎样？
5. **对比澄清**：和已有的方案 X 有什么区别？为什么不选 X？
6. **具体化**：能给我一个数字吗？能举个真实例子吗？用代码说？
7. **动机追问**：为什么要做这个？不做会怎样？

### 3. 控制节奏

- 每轮抛 1-2 个问题，**不要一次问 10 个**
- 用户答完后再选下一个角度
- 不要在同一个角度反复追问——答不清就换个角度

### 4. 决定何时停止

N 轮后（默认 5 轮）总结：

- **澄清出了什么**：列清楚的问题点
- **还模糊什么**：没答清的地方
- **建议下一步**：调哪个 Skill（design / research / requirement / coding）

如果用户中途说「够了 / 我说清楚了」，立刻停止。

## 输出格式

每轮用简短中文：

```markdown
# Grill: <主题>

**已进行**：N 轮

## 本轮追问

**方向**：前提质疑 / 证据要求 / 反例构造 / ...

**问题**：
- [问题 1]
- [问题 2（如有）]

> 等用户回答后再继续。
```

N 轮后的总结：

```markdown
## 总结

### 已澄清
- [点 1]
- [点 2]

### 仍模糊
- [盲点 1]

### 建议下一步
调 `design` Skill 基于已澄清的部分产出方案；
对仍模糊的部分先做一轮 requirement 或 research。
```

## 行为准则

- **不替用户想**：问清楚比答出来更重要
- **问具体而非抽象**：避免「你怎么考虑这个」，问「能给我一个数字吗」
- **承认答得清**：用户答得清楚就大方承认，不要为了显得深刻继续追问
- **不假装质疑**：如果用户回答已经充分，直接进下一轮或停止
- **不输出方案**：grill 只澄清问题；给方案是其它 Skill 的事

## 不要做的事

- 不要给技术方案（属于 `design`）
- 不要做技术调研（属于 `research`）
- 不要写代码或伪代码
- 不要为「显得深刻」问刁钻问题
- 不要在用户已经清楚时还追问
- 不要把 grill 的输出当作最终答案交付

## 与其它 Skill 的关系

| Skill | 关系 |
|---|---|
| `requirement` | 上游：grill 后需求还不清，调 requirement 整理 |
| `design` | 下游：grill 后调 design 给方案 |
| `research` | 下游：grill 后调 research 做技术调研 |
| `review` | 互补：review 审代码，grill 审想法 |
| `debug` | 互补：debug 找 Bug 根因，grill 找想法漏洞 |

## 风格参考

借鉴 mattpocock/skills 的 `grill-me`：

- 不接受「差不多」
- 不接受「应该是吧」
- 不接受「大家都这么做」
- 永远要具体、要证据、要反例

但比 `grill-me` 克制：每轮只 1-2 个问题，给用户思考空间。

# Design

接收 `requirement` Skill 的输出或已有的需求文档，产出可评审的技术设计。

## 何时使用

- 需求文档已经清楚，进入方案设计阶段
- 现有架构需要演进，要先评估几种走向
- 需要评估可行性或技术风险
- 在写代码前对齐团队思路

不要用于：

- 还没澄清需求（先 requirement）
- 只改几行代码的小改动

## 匹配边界

按最终交付物选择：

| 用户要的结果 | 使用 |
|---|---|
| 系统架构、组件边界、技术选型、关键技术流程 | `design` |
| 页面交互、布局、颜色、排版和视觉规范 | `design-interface` |
| API 端点、字段、错误码和版本契约 | `api-design` |
| Schema、Migration、索引和查询方案 | `database` |
| LLM 上下文选择、排序、压缩、记忆与 Token 预算契约 | `context-engineering` |
| 可运行的源代码或实际文件修改 | `coding` |

用户说“设计”不代表一定使用本 Skill；必须先判断用户要的是技术方案、界面方案还是实际实现。

## 流程

1. **回顾需求**：列出核心功能、非功能约束、依赖
2. **架构总览**：用一张图（或一段文字）描述系统由哪几部分组成、各自职责
3. **接口设计**：定义对外 API 的端点、请求 / 响应、错误码、鉴权方式
4. **数据模型**：核心实体、关系、关键字段；用 ER 图或表格
5. **关键算法 / 流程**：对最复杂或最容易出错的部分，写清步骤和边界
6. **技术选型**：候选方案、对比维度、结论（避免空泛的「业界常用」）
7. **风险与缓解**：列出可能延期或失败的事项，以及预案
8. **落地计划**：阶段拆分、依赖顺序、可并行项

## 输出格式

```markdown
# 技术设计

## 背景与目标
[引用需求文档；说明本次设计要解决的核心问题]

## 架构总览
[图或文字描述各组件与边界]

## 接口设计
[端点、字段、错误码、鉴权]

## 数据模型
[实体 / 关系 / 关键字段]

## 关键流程
[最难或最关键的部分]

## 技术选型
| 候选 | 优点 | 缺点 | 结论 |

## 风险与缓解
| 风险 | 概率 | 影响 | 缓解措施 |

## 落地计划
- [ ] 阶段 1：...
- [ ] 阶段 2：...
```

## 行为准则

- **先有结论**：开头用一段话讲清「我们打算怎么做」，再展开细节
- **对比而非堆叠**：选型要给出对比，不能只列优缺点不结论
- **承认不确定性**：未确定的部分直接标 TODO，而不是假装确定
- **可评审**：每节都要能让别人快速判断对错，而不是只描述「思路」

## 不要做的事

- 不要写代码（那是 coding）
- 不要在设计里写注释掉的伪代码代替方案
- 不要为了显得完整而加无关的可选项

# Codebase Exploration

围绕当前任务建立一张可追溯的代码库地图，让后续工作知道“从哪里进入、沿什么链路阅读、哪些文件最相关”。

## 何时使用

- 第一次接触仓库，需要快速理解它如何组织和运行
- 接手任务前，需要定位入口、模块边界和关键调用链
- 用户询问某项能力在项目中的实现位置或运行路径
- 需要为后续设计、调试、影响分析或实现建立上下文

不要用于：

- 设计 Agent 运行时选入哪些代码、文档、记忆和工具结果（用 `context-engineering`）
- 查阅外部资料或比较技术方案（用 `research`）
- 评估一个拟议修改会影响哪些调用方和契约（用 `change-impact-analysis`）
- 设计新的架构或模块接口（用 `design` / `codebase-design`）
- 新增或修改实际代码（用 `coding`）
- 只压缩用户已经提供的材料（用 `summary`）

## 探索深度

默认采用**任务聚焦探索**：先建立全局骨架，再只深入与用户目标相关的路径。

- **快速扫描**：目录、技术栈、入口、构建与测试命令
- **任务聚焦**：追踪与当前问题相关的符号、调用链和数据流
- **全局地图**：仅在用户明确要求项目全景时扩展到全部核心模块

## 流程

1. **锁定探索目标**：把用户问题改写成需要回答的 2-5 个导航问题，明确范围与停止条件
2. **读取仓库规则**：优先读取 `AGENTS.md`、README、Manifest、构建配置和目录内局部说明
3. **建立骨架**：识别顶层目录、语言与框架、应用入口、构建入口、测试入口和部署入口；跳过依赖、生成物和大体积无关文件
4. **定位任务锚点**：使用文件名、符号、路由、配置键、错误文本或领域术语找到最相关文件
5. **追踪关键链路**：从入口沿 import、调用、事件、数据访问或配置引用向下追踪；必要时反向查找调用方
6. **提取项目约定**：记录目录分层、命名、错误处理、测试组织、配置和依赖注入方式
7. **标注证据与未知项**：关键判断附文件路径和符号；无法确认的内容明确列为未知，不用猜测补齐
8. **输出导航报告**：回答最初的导航问题，并给出后续最值得阅读的文件顺序

完成标准：用户提出的每个导航问题都有代码证据、相关文件和明确结论；未确认项被单独标记。

## 输出格式

```markdown
# Codebase Navigation

## 探索目标
- [问题 / 范围]

## 项目骨架
- 技术栈：...
- 运行入口：`path` — [作用]
- 构建 / 测试入口：...

## 核心模块
| 模块 | 职责 | 关键文件 | 依赖关系 |
|---|---|---|---|

## 关键调用链
1. `入口符号`（path）
2. `服务 / 处理器`（path）
3. `数据或外部依赖`（path）

## 项目约定
- [约定 + 证据]

## 任务相关文件
1. `path` — [为什么先读]

## 未确认项
- [缺少什么证据 / 如何确认]
```

## 行为准则

- **先地图后细节**：没有全局骨架前，不在单个文件里无限下钻
- **证据优先**：用路径、符号和引用关系支撑结论
- **按需停止**：达到探索目标后停止，不把探索变成无边界审计
- **只读优先**：探索阶段不修改代码，不把发现的问题顺手修掉

# Review

对一段代码改动做结构化审查，覆盖「规范」与「需求」两个独立轴。

## 何时使用

- 一段改动完成、准备提交或合并前
- 收到 PR / MR，需要审阅
- 重构后想确认行为没变
- 定期巡检关键模块

不要用于：

- 还没写完的代码
- 一次性格式调整（用 lint）
- 键盘、焦点、语义和屏幕阅读器等专项审计（用 `accessibility-audit`）
- 个人信息目的、最小化、保留、删除和共享等专项审查（用 `privacy-review`）
- 漏洞、攻击面、权限和注入等专项审查（用 `security`）
- 只需实际运行质量门禁并判断是否可交付（用 `verification`）

## 两条审查轴

**规范轴（Standards）**：本次改动是否遵守了项目的编码规范。规范源包括：

- 仓库的 `CODING_STANDARDS.md` / `CONTRIBUTING.md` 等文档
- `~/.agents/knowledge/coding-style/` 中的通用基线
- 已有代码体现出的隐性约定

**需求轴（Spec）**：本次改动是否忠实实现了原始 issue / PRD / 描述。

- 缺了什么
- 多做了什么（scope creep）
- 看起来实现了但实现错的

两轴独立运行、互不污染，最后再合并展示。

## 流程

1. **锁定基线**：用户给的起点（commit、分支、tag）；没指定就问。确认 `git diff` 非空且能解析
2. **定位规范源**：扫描仓库文档 + AOS knowledge
3. **定位需求源**：从 commit message、文件名、PRD、用户提供的描述里找
4. **两轴并行审查**：分别给两段独立的发现
5. **合并展示**：每条发现给出严重程度、所在位置、修改建议

## 输出格式

```markdown
# Review Report

## 基线
- 起点：[commit / 分支]
- 改动文件数：N

## Standards（规范）
- [Severity] 文件:行 — 问题 — 建议
- ...

## Spec（需求）
- [Severity] 文件:行 — 与需求 §x 不符 — 建议
- ...

## 总结
- Standards: N 项（最严重：...）
- Spec: N 项（最严重：...）
```

## 严重程度

- **Blocker**：必须修复才能合并
- **Major**：强烈建议修复
- **Minor**：可后续清理
- **Nit**：风格问题

## 行为准则

- **不臆测意图**：看不懂就问，而不是脑补
- **不夹带私货**：风格偏好不算 issue
- **建议而非命令**：给出修改方向，不要替别人写代码
- **承认看错**：发现误判立刻撤回

## 不要做的事

- 不要在审查里改代码
- 不要把 lint 能查的事也报一遍
- 不要为了显得专业罗列一堆「可能有问题」

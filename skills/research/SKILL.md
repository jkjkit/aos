# Research

对「选哪个技术 / 用哪种方案」做结构化研究，输出可被评审的对比和推荐。

## 何时使用

- 需要在多个候选之间做选型（库、框架、架构模式）
- 想评估一项新技术的适用性
- 遇到陌生的技术挑战，要先搞清楚背景
- 团队对方案有分歧，需要中立对比

不要用于：

- 已知答案的常识性问题
- 一次性的探索性 PoC（直接做）
- 只需建立现有仓库的目录、入口和调用链地图（用 `codebase-exploration`）

## 流程

1. **明确问题**：把要研究的问题写成一两句话的成功标准
2. **列出候选**：先列 3-5 个候选；过少会遗漏，过多难对比
3. **确定评估维度**：功能、性能、学习成本、运维成本、风险、社区活跃度
4. **收集证据**：官方文档、benchmark、issue 列表、团队经验、已采用案例
5. **加权打分**：给每个维度权重（团队具体情况），逐项打分
6. **POC 验证**：对前 1-2 名做最小可运行验证
7. **输出推荐**：明确推荐 + 关键风险 + 何时该重新评估

## 输出格式

```markdown
# 技术调研：[主题]

## 问题
[要解决什么、成功标准是什么]

## 候选
- A：[简介 + 官网]
- B：[简介 + 官网]
- C：[简介 + 官网]

## 评估维度与权重
| 维度 | 权重 |
|------|------|
| 功能匹配 | 25% |
| 性能 | 15% |
| 学习成本 | 15% |
| 运维成本 | 15% |
| 风险 | 15% |
| 社区 | 15% |

## 对比矩阵
| 维度 | A | B | C |
|------|---|---|---|
| 功能 | 4 | 5 | 3 |
| 性能 | 5 | 3 | 4 |
| ... | | | |
| 加权总分 | 4.1 | 4.0 | 3.6 |

## 关键证据
- A：[来源 + 关键发现]
- B：[来源 + 关键发现]

## POC 结果
- A：跑了 [case]，表现 X
- B：跑了 [case]，表现 Y

## 建议
推荐 **B**，理由：
1. ...
2. ...

## 风险与重评条件
- 风险：...
- 什么时候重新评估：[团队规模 > N / 需要 X 特性 / ...]
```

## 行为准则

- **带数字**：性能 / 包大小 / 学习曲线尽量给具体数据
- **标来源**：每个论断要可追溯到文档、issue、benchmark
- **承认局限**：自己没用过的标「未实测」，别假装熟悉
- **给推荐**：研究的目的不是「列优缺点」而是「得出选择」

## 不要做的事

- 不要列优缺点不下结论
- 不要把所有维度都设为「重要」——权重必须区分
- 不要把「业界常用」当论据——业界常用也可能错
- 不要跳过 POC 只靠文档对比

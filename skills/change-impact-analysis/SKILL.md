# Change Impact Analysis

在动手修改前画出变更的爆炸半径，确保受影响的代码、契约、数据和交付环节都被纳入计划。

## 何时使用

- 修改公共函数、共享模块、配置、数据结构或跨模块行为前
- API、事件、数据库 Schema 或序列化格式将发生变化
- 需要判断“改这里还会影响哪里”或估算变更范围
- 准备重构、升级依赖或迁移时，需要确定兼容性和回归重点

不要用于：

- 只想理解代码库结构和调用链（用 `codebase-exploration`）
- 审查已经完成的代码或 diff（用 `review`）
- 评估业务、合规、财务等广义项目风险（用 `risk-analysis`）
- 设计目标架构或具体实现方案（用 `design`）
- 编写测试策略与测试代码（用 `testing`）

## 输入

至少需要以下之一：

- 拟修改的行为、符号、文件或配置
- 目标 API、Schema、事件或依赖版本
- 预期的“修改前 → 修改后”差异

如果变更意图仍不明确，先确认变化是什么，再分析影响；不要把多个假设混成一个结论。

## 流程

1. **定义变更单元**：描述当前行为、目标行为、明确不变的部分和兼容性要求
2. **定位变更锚点**：找到实现、声明、配置、Schema、生成物和所有权边界
3. **分析直接影响**：查找调用方、实现方、导入方、读写方、测试和文档
4. **分析间接影响**：沿数据流、事件、缓存、权限、错误处理、序列化和运行配置继续追踪
5. **检查外部契约**：覆盖 API、CLI、事件、数据库、文件格式、环境变量及第三方集成
6. **检查交付链路**：覆盖迁移、回滚、监控、发布顺序、灰度和向后兼容
7. **分级与标信心**：按严重度、发生条件和证据强度标记确认影响、可能影响与未知项
8. **给出验证清单**：为每项影响指定应执行的检查，但不在本 Skill 中编写完整测试实现

完成标准：每个已知变更面都能对应到受影响对象、证据、处理动作和验证方法；未知项有明确的确认路径。

## 影响维度

| 维度 | 检查内容 |
|---|---|
| 代码 | 调用方、继承/实现、共享工具、错误路径 |
| 契约 | API、事件、CLI、文件格式、序列化、版本兼容 |
| 数据 | Schema、Migration、历史数据、回填、缓存 |
| 配置 | 环境变量、Feature Flag、权限、默认值 |
| 测试 | 单元、集成、E2E、契约测试、快照 |
| 交付 | 构建、部署顺序、监控、回滚、运维手册 |
| 文档 | 用户指南、API 文档、迁移说明、变更日志 |

## 输出格式

```markdown
# Change Impact Report

## 拟议变更
- 当前：...
- 目标：...
- 不变项：...

## 影响矩阵
| 受影响对象 | 影响类型 | 严重度 | 证据 | 所需动作 | 验证方式 |
|---|---|---|---|---|---|

## 兼容性与发布
- 破坏性变更：是 / 否 / 未确认
- Migration：...
- 发布顺序：...
- 回滚条件：...

## 未确认项
- [未知项 + 确认方法]

## 建议变更范围
- 必须修改：...
- 可能修改：...
- 明确不改：...
```

## 行为准则

- **双向追踪**：既看依赖了什么，也看谁依赖它
- **契约优先**：公共边界的变化比内部实现变化更需要优先确认
- **区分事实与推断**：没有引用证据的影响标记为“可能”或“未知”
- **不扩大方案**：只分析影响，不借机重做架构设计

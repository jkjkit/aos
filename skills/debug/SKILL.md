# Debug

排查难复现 Bug 和性能回退的纪律性流程。阶段不可随意跳过，除非有明确理由。

## 第一原则：先建立反馈环

> 一切排查技术（bisect、假设、插桩）都只是在「消耗」这个反馈环。如果环不紧，再多努力也是空转。

反馈环是一个**能在你这次 Bug 上变红、修好之后变绿**的可重复命令。投入不成比例的精力把它做紧。

### 反馈环的形式（按推荐顺序）

1. **失败用例**：unit / integration / e2e 中能触发 Bug 的那条
2. **curl / HTTP 脚本**：对开发态服务的真实请求
3. **CLI + fixture**：输入一个固定文件，diff 输出和已知正常版本
4. **无头浏览器脚本**：Playwright / Puppeteer，断言 DOM / console / network
5. **回放 trace**：把生产请求体 / 事件日志存盘，重放进代码路径
6. **最小 harness**：只起 Bug 路径上的一个服务，依赖全 mock
7. **fuzz / property loop**：随机输入 1000 次，统计失败模式
8. **bisect harness**：能 `git bisect run` 的「在某状态启动 → 检查 → 重复」
9. **diff 回路**：同输入跑新旧版本对比输出
10. **HITL bash**：万不得已，让人手动点击也要套进 `hitl-loop.template.sh`

### 反馈环要越做越紧

拿到一个粗糙的环之后，继续优化：

- 能不能更快（缓存、跳过无关初始化、缩窄测试范围）
- 能不能信号更锐（断言用户描述的精确症状，而不是「没崩」）
- 能不能更确定（固定时间、固定随机数、隔离文件系统、冻结网络）

30 秒的不稳定环 ≈ 没有环；2 秒的确定性环 = 调试超能力。

### 非确定性 Bug

目标不是「稳定复现」，而是**提高复现率**。把触发条件跑 100 遍，并行、加压、缩窄时间窗口、注入 sleep。50% 概率能复现的可调试，1% 不可调试。

### 实在建不出环怎么办

停下来明确说「建不出」。列尝试过的事，向用户索取：

- 能复现的环境
- 已捕获的产物（HAR、日志、core dump、带时间戳录屏）
- 临时在生产插桩的许可

**没有环不要进入第二阶段**。

### 完成标志

能说出**一条命令**（脚本路径、test 调用、curl），并且**已经至少跑过一次**（贴出调用和输出），满足：

- [ ] **能变红**：覆盖实际 Bug 路径，断言用户精确症状
- [ ] **确定性**：每次跑结果一致
- [ ] **快速**：秒级，不是分钟级
- [ ] **Agent 可跑**：可以无人值守运行

如果还没建立这个命令就开始读代码猜原因——**停下**。直接跳到假设 = 这个 Skill 想要阻止的失败。

## 流程

### 阶段 1 — 反馈环

见上文。

### 阶段 2 — 复现 + 最小化

跑环，看到变红。确认：

- [ ] 失败模式与用户描述一致（不是另一个碰巧相邻的失败）
- [ ] 多次跑都能复现（非确定性 Bug 至少高复现率）
- [ ] 抓住了精确症状（错误消息、错误输出、慢在哪里）

然后最小化：每次只删一个输入 / 调用者 / 配置 / 数据 / 步骤，重跑环，**只留下对失败承重的部分**。最小化后，每个剩下的元素都是承重的——去掉任意一个环就变绿。

### 阶段 3 — 假设

**在测试任何假设之前**先列 3-5 个排序后的假设。单假设会锚定在第一个「听起来合理」的想法上。

每个假设都要可证伪，写出预测：

> 如果 X 是原因，那么改变 Y 会让 Bug 消失 / 改变 Z 会让 Bug 加重。

说不清预测的假设是「氛围」，丢掉或打磨。

把排序结果展示给用户（领域知识常常瞬间重排），不要等批准——用户不在就按自己排序继续。

### 阶段 4 — 插桩

每个探针对应阶段 3 里的一条预测。**一次只改一个变量**。

工具偏好：

1. Debugger / REPL 断点（一个断点胜过十条日志）
2. 在区分假设的边界点打定向日志
3. 永远不要「全打日志再 grep」

每个调试日志带唯一前缀，例如 `[DEBUG-a4f2]`。结束时清理就是一条 grep。

**性能分支**：性能回退通常不适合打日志。改成建立基线（计时器、`performance.now()`、profiler、查询计划），然后 bisect。先量后修。

### 阶段 5 — 修复 + 回归测试

**先写回归测试再修**——但只在「正确 seam」存在时。

正确 seam = 测试能在调用现场覆盖真实的 Bug 模式。如果唯一可用的 seam 太浅（单调用方测试，但 Bug 需要多调用方；单元测试复现不出触发的链路），那里的回归测试给的是虚假安全感。

**没有正确 seam 本身就是发现**。记录下来。架构正在阻止 Bug 被锁死。把它交给 `/improve-codebase-architecture`。

如果有正确 seam：

1. 把最小复现转成该 seam 上的失败用例
2. 看它失败
3. 应用修复
4. 看它通过
5. 重新跑阶段 1 的环，对原始（非最小化）场景再验证

### 阶段 6 — 清理 + 复盘

宣布完成前必做：

- [ ] 原始复现已不再复现（重跑阶段 1）
- [ ] 回归测试通过（或记录「无 seam」）
- [ ] 所有 `[DEBUG-...]` 插桩已清除（grep 前缀）
- [ ] 一次性原型已删除（或移到明显标记的 debug 目录）
- [ ] 哪个假设最终被证实，写进 commit / PR message——让下一个调试者学到

**再问一句：什么本来可以阻止这个 Bug？** 如果答案涉及架构变更（没有好 seam、调用链纠缠、隐藏耦合），把具体情况交给 `/improve-codebase-architecture` skill。修复落定后再提建议——你比开始时信息更多。

## 不要做的事

- 不要在阶段 1 之前开始读代码
- 不要同时改多个变量
- 不要在没环的情况下猜
- 不要留下任何 `[DEBUG-...]` 前缀的日志

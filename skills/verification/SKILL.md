# Verification

用实际执行证据回答“这项工作是否真的完成并可交付”，而不是依据代码外观或口头声明判断。

## 何时使用

- 代码或配置修改完成，需要做最终交付检查
- 用户要求运行构建、类型检查、lint、测试或验收命令
- 需要确认实现是否满足明确的验收标准
- 合并、发布或交接前，需要形成可复现的验证记录

不要用于：

- 设计测试策略、测试用例或编写测试代码（用 `testing`）
- 审查代码质量、规范和需求实现方式（用 `review`）
- 已知命令失败后深入定位根因（用 `debug`）
- 为 LLM、Prompt、RAG 或 Agent 新建评估集、指标、评估器和质量门禁（用 `llm-evaluation`）
- 修复实现或调整代码使检查通过（用 `coding`）

## 验证原则

- **运行过才算证据**：未执行的检查不能写成通过
- **项目命令优先**：优先使用仓库脚本、CI 配置和贡献文档定义的命令
- **逐层升级**：先运行快速、局部检查，再运行构建和更广泛测试
- **结果可复现**：记录准确命令、范围、退出状态和关键输出
- **失败即保留**：不要修改测试或降低阈值来制造绿色结果

## 流程

1. **建立完成契约**：收集用户验收标准、任务说明和项目质量门禁，列出必须验证的项目
2. **发现验证入口**：读取包管理脚本、Makefile、CI、测试配置和仓库说明，确认环境前提
3. **规划执行顺序**：通常按格式/静态检查 → 类型检查 → 构建 → 定向测试 → 全量测试 → 手工验收排列
4. **执行并记录**：逐条运行命令，保留退出码、耗时、关键结果和跳过原因
5. **映射验收标准**：把每条验收条件关联到自动检查、人工检查或现有证据
6. **分类失败**：区分实现失败、环境阻塞、缺少依赖和疑似既有失败；只做最小复核，不在此阶段展开根因修复
7. **检查遗漏**：确认没有把“未运行”“不适用”和“通过”混为一谈
8. **给出结论**：仅当所有必需项通过时标记 Passed；存在失败为 Failed；存在必需但未验证项为 Incomplete

完成标准：每个必需质量门禁和验收条件都有 Passed、Failed、Not Run 或 Not Applicable 状态，并附可核查证据。

## 输出格式

```markdown
# Verification Report

## 范围
- 变更 / 任务：...
- 完成条件：...

## 自动检查
| 检查 | 命令 | 状态 | 关键证据 |
|---|---|---|---|
| Lint | `...` | Passed / Failed / Not Run | ... |

## 验收映射
| 验收条件 | 验证方式 | 状态 | 证据 |
|---|---|---|---|

## 失败与未验证项
- [状态] [项目] — [原因 / 下一步]

## 结论
**Passed / Failed / Incomplete**

[一句话说明是否可以交付]
```

## 状态定义

- **Passed**：命令或验收动作已执行且结果符合要求
- **Failed**：已执行但结果不符合要求
- **Not Run**：应该验证但因环境、权限、时间或缺少依赖未执行
- **Not Applicable**：有明确理由证明该检查不适用于本次变更

## 行为准则

- **不伪造绿色**：不能运行时报告 `Not Run`，不要根据经验猜测会通过
- **不越界修复**：发现失败后提供最小诊断信息并转交 `debug` 或 `coding`
- **不遗漏手工验收**：无法自动化的视觉、交互或业务结果仍要进入验收映射
- **结论保守**：一个必需项未验证，整体结论就是 `Incomplete`

# Dependency Management

制定第三方依赖的引入、升级、替换与淘汰策略，控制供应链风险与维护成本。

## 何时使用

- 决定是否引入新依赖（npm / pip / go mod / cargo 等）
- 现有依赖大版本升级
- 依赖不再维护，需要替换
- 漏洞公告需要紧急响应
- 依赖膨胀需要瘦身

不要用于：

- 漏洞扫描与具体修复（用 `dependency-audit`）
- 框架整体升级（用 `migration`）

## 引入决策

引入新依赖前，回答 5 个问题：

1. **必要性**：能不能用现有依赖或标准库解决？3 行 util 不需要 50 KB 的库
2. **维护活跃度**：最近一次发布 < 3 个月；issue 响应 < 1 周；star / fork 健康
3. **许可证兼容**：MIT / Apache 2.0 / BSD 安全；GPL / AGPL 可能影响商业产品
4. **依赖树**：传递依赖多少？有没有冲突？体积是否可接受
5. **退路**：库死了怎么办？能否替换？锁版本能管多久

只有 5 个问题都过关才引入。

## 升级策略

升级类型与策略：

| 升级类型 | 策略 |
|----------|------|
| Patch（补丁） | 自动升级；CI 验证通过即可 |
| Minor（小版本） | 每周批量升级；CHANGELOG 快速 review |
| Major（大版本） | 单独立项；写迁移指南；灰度发布 |

升级纪律：

- **锁版本**：生产锁定精确版本；非生产可用 `^`
- **渐进升级**：不要一次跳多个 major
- **记录 Breaking Change**：每个 major 升级写一行为什么升、什么变了
- **失败即回滚**：升级导致 CI 红 / 性能回退，立即回退

## 淘汰策略

定期审视依赖：

- **未使用**：tree-shaking 后仍引入；标记删除
- **未维护**：> 1 年无发布；找替代
- **重复功能**：两个库做同一件事；选一个
- **自实现更划算**：库复杂、调用面窄；改成自实现

## 输出格式

```markdown
# Dependency Plan

## 当前依赖盘点
- 总数：N
- 直接依赖：M
- 传递依赖：K
- 待升级：L
- 已知漏洞：J

## 引入决策

### 候选：[库名]
1. 必要性：✅ / ❌
2. 维护活跃：...
3. 许可证：...
4. 依赖树：...
5. 退路：...
- 结论：引入 / 拒绝 / 暂缓

## 升级计划

### Patch 批量升级
- 范围：[列表]
- 时间：本周内
- 验证：CI

### Major 升级
- 库：从 v2 → v3
- 风险：Breaking change（描述）
- 迁移：[指南链接]
- 灰度：内部 → 预发 → 生产
- 回滚：[命令]

## 淘汰清单
- [库]：未使用 / 重复 / 自实现
- 时间：下次迭代删除

## 漏洞响应
- 监控：Dependabot / Renovate / npm audit
- 响应 SLA：Critical 24h，High 7d，Medium 30d
- 流程：见 `dependency-audit` Skill
```

## 行为准则

- **少即是多**：依赖越少越安全
- **版本可重现**：`lock` 文件必须入库
- **声明许可证**：所有依赖列在 NOTICE / LICENSE 文档
- **监控是常态**：CI 跑 audit；Dependabot 自动 PR
- **退路先于引入**：选库时想好怎么扔

## 不要做的事

- 不要引入 `latest` 标签到生产
- 不要为了省 10 行代码引入 1 MB 的库
- 不要在 lock 文件里手动改版本
- 不要忽略 GPL / AGPL 依赖
- 不要把传递依赖当直接依赖使用（pin 上去）

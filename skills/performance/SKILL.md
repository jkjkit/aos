# Performance

分析性能瓶颈、提出可执行的优化方案，并用基线对比验证效果。

## 何时使用

- 接口响应时间不达预期
- 系统吞吐或并发能力受限
- 资源占用（CPU / 内存 / IO）异常
- 需要为关键路径建立性能基线
- 上线前做容量评估

不要用于：

- 业务功能未稳定（先完成 coding 与 testing）
- 偶发性崩溃或错误（用 debug）
- 安全漏洞排查（用 security）

## 流程

1. **定义指标**：延迟（P50 / P95 / P99）、吞吐（QPS）、资源占用——明确要优化什么
2. **收集现状**：监控、日志、trace；拿到数字再说，不要凭印象
3. **复现路径**：在测试或预发环境复现慢场景；记录复现条件
4. **定位瓶颈**：
   - 应用层：算法复杂度、循环、阻塞调用、并发模型
   - 数据层：慢查询、N+1、缺失索引、锁等待
   - IO 层：网络、磁盘、序列化
   - 资源：CPU、内存、连接池
5. **提出方案**：列出可执行的优化动作，标预期收益和风险
6. **验证**：写基准测试；优化前/后对比；至少两次独立测量
7. **输出报告**：瓶颈分析、优化项、验证结果、监控建议

## 输出格式

```markdown
# Performance Report

## 现象
[慢 / 高 CPU / 高内存 + 触发条件]

## 瓶颈定位
- 层：应用 / 数据 / IO / 并发
- 根因：[描述]
- 证据：[监控 / trace / 截图]

## 优化方案

### OPT-001：[标题]
- 层：应用 / 数据 / IO
- 动作：[具体改法]
- 预期收益：[估算，如 P95 5s → 200ms]
- 风险：Low / Medium / High

### OPT-002：...

## 验证
- 基准：[方法]
- Before：[数字]
- After：[数字]

## 监控建议
- [指标 1]
- [指标 2]
```

## 常见瓶颈速查

| 现象 | 优先查 |
|------|--------|
| 单接口慢 | DB 查询 / 远程调用 / N+1 |
| CPU 高 | 热点循环 / 序列化 / JSON 处理 |
| 内存涨 | 大对象缓存 / 泄漏 / 队列堆积 |
| 延迟抖动 | GC / 锁竞争 / 慢上游 |
| 容量上不去 | 连接池 / 线程模型 / 同步阻塞 |

## 行为准则

- **先量后修**：没有基线数字不开始优化
- **一次改一个变量**：避免混淆因果
- **记录环境**：硬件、数据量、并发数；不可重复的「优化」无效
- **承认无收益**：测完没效果就老实说，不要硬凑结论

## 不要做的事

- 不要改业务逻辑来「优化」——那是 bug 风险
- 不要在生产直接试优化方案
- 不要把「看起来更优雅」当作优化
- 不要忽略 P99——平均好看但尾巴长很常见

# Design Interface

设计界面的完整方案——交互流程与视觉规范。**不写代码，不设计 API，不做系统架构**。

## 何时使用

- 新页面 / 新组件需要完整设计
- 现有界面风格不统一需要对齐
- 用户描述模糊，需要先翻译再设计
- 跨团队评审需要标准化输出

不要用于：

- 写代码实现（用 `coding`）
- API 契约设计（用 `api-design`）
- 系统架构（用 `design`）
- 数据库 Schema（用 `database`）
- 对现有界面执行键盘、焦点、屏幕阅读器、对比度和缩放审计（用 `accessibility-audit`）
- 单纯澄清需求（用 `grill`）

## 匹配边界

本 Skill 的交付物是**界面方案**，不是代码。

- “设计一个登录页的交互和视觉规范” → `design-interface`
- “实现 / 开发 / 写出一个登录页” → `coding`
- “设计登录系统的服务和数据流” → `design`
- “定义登录接口” → `api-design`

即使任务涉及前端，只要用户要求直接修改项目文件或交付可运行页面，就应选择 `coding`。

## 核心原则

借鉴自一线设计沟通经验：

- **翻译优先于直接设计**：用户说「高级一点」，先翻译成「低饱和度 + 大留白 + 无装饰」，再开始画
- **量化胜过形容词**：用「8px 间距」而非「紧凑一点」，用「对比度 4.5:1」而非「看得清」
- **约束胜过创意**：每多一条可量化的「不要做」，结果就越可控
- **可访问性是底线**：对比度、键盘可达、焦点可见不可商量

## 流程

### 1. 澄清意图

在画任何东西之前，先把用户的描述从「感觉层」翻译到「规范层」。

感觉层（最模糊）：

- 「高级一点」「舒服一些」「看着洋气」「活泼」「专业」

规范层（最确定）：

- 「主色 #4A3FCC」「8pt 网格」「行高 1.7」「圆角 8px」「最多 6 个颜色角色」

**目标是引导用户从感觉层走到规范层。** 可以问：

- 「你说的『高级』，是指少用色、还是多用留白？」
- 「能给我一个具体的颜色吗？或者一个参考产品？」

如果用户答不出具体，就先给可量化的默认值。

### 2. 设计 token

先把约束定下来，不要边画组件边定 token。

#### 色彩

- 主色 1 个 + 中性色 5-9 阶
- 语义色：success / warning / danger / info
- 颜色角色不超过 6 个：主色、强调色、背景、表面、正文、次要
- 强调色占比 ≤ 10%
- 正文与背景对比度 ≥ 4.5:1

#### 字体

- 字体族最多 2 个
- 字号阶梯用 1.2-1.3 倍递增（避免中间档）
- 正文 16px / 行高 1.6-1.7 / 字重 400
- 标题与正文字号比 ≥ 2 倍

#### 间距

- 8pt 网格为主，小间距可用 4
- 组件内部 8-16px，组件之间 24-32px，大区块 48-64px

#### 圆角与阴影

- 圆角选一种风格贯穿（硬朗 0-4 / 标准 8 / 亲和 12-16 / 胶囊 full），不要混
- 阴影 3-4 档足够，不要五彩斑斓的 glow

### 3. 用户旅程与状态机

每个关键交互对象明确：

- **状态清单**：empty / loading / error / success / partial
- **触发条件**：什么事件导致状态转换
- **每个状态**：显示什么 / 允许什么操作
- **边界状态**：超时、网络断开、并发、权限变更

只设计 happy path 是不够的——大多数失败来自未覆盖的状态。

### 4. 组件设计

每个组件明确：

- 状态：default / hover / active / focus / disabled / loading / error
- 尺寸：sm / md / lg（不超过 3 个）
- 变体：primary / secondary / ghost（最多 2-3 个）
- 内容边界：最长 / 最短 / 空状态

### 5. 微交互

| 操作 | 反馈 | 时长 |
|------|------|------|
| 按钮点击 | 按下 + 颜色变化 | ~100ms |
| 表单提交 | Loading + 禁用重复提交 | 直到响应 |
| 成功 | Toast + 自动消失 | ~3s |
| 失败 | 内联错误 + 焦点定位 | 持续 |

超过 200ms 的操作必须给 loading。超过 10 秒要给进度或可取消。

### 6. Anti-Slop 检查

提交前自查：

- [ ] 没有紫色到蓝色渐变（典型 AI 味）
- [ ] 没有居中堆叠（表格 / 表单 / 列表应该左对齐）
- [ ] 没有滥用 glassmorphism
- [ ] 阴影不超过 4 档
- [ ] 颜色不超过 6 个角色
- [ ] 字体不超过 2 个字体族
- [ ] 设计稿展示真实数据形态（真实名字、真实长度的字符串）
- [ ] 包含 empty / error / loading 状态

### 7. 输出设计规格

不要交付「设计思路」「视觉感受」这种抽象描述——交付可被工程师照着实现的规格文档。

## 输出格式

```markdown
# Design Spec: <页面 / 组件>

## 目标
[一句话：给谁用，完成什么任务]

## 风格
[风格名 + 情绪词 + 对标产品或参考]

## 布局
- 整体：[单列 / 双列 / 网格 / 左导航右内容]，最大宽度 [px]
- 首屏：[分区描述]
- 后续区块：[依次列出]

## 配色
- 背景：[色值]   表面：[色值]
- 主色：[色值]（用于 [按钮 / 链接]）
- 强调色：[色值]（仅用于 [行动召唤]，占比 ≤ 10%）
- 文字：主 [色值] / 次要 [色值]

## 字体
- 标题 [衬线 / 无衬线] [字重]，正文 [无衬线]，[px] / 行高 [值]
- 代码：等宽字体

## 细节
- 间距基准：8pt 网格，组件间 24px，区块间 48px
- 圆角：[px]   阴影：[层级]
- 交互：[hover 效果]，[时长]ms 缓动

## 组件清单
[按钮 / 表单 / 卡片 / 导航 / 反馈]

## 状态机
[关键交互对象的状态转换]

## 约束
- [移动端优先]
- [仅用上述配色]
- [不引入额外颜色]
- [不使用装饰性动效]
```

## 行为准则

- **翻译先行**：用户说「高级」，先翻译成规范再设计
- **量化优先**：用数字而非形容词
- **先 token 后组件**：没有 token 不要画组件
- **真实数据**：用真实名字、真实长度的字符串测试
- **对齐胜过装饰**：留白和对齐比花哨效果更显高级
- **可访问性不可省**：对比度、键盘、焦点

## 不要做的事

- 不要把感觉层描述原样传给执行方
- 不要给同一组件 3+ 种变体
- 不要用占位文字「文本」「标题」
- 不要忽略空状态与错误状态
- 不要输出未经量化的设计
- 不要为追求「好看」破坏可读性
- 不要照搬外部 Skill 的具体结构——只学思考方式

## 逆向模式（Reverse Mode）

正向设计是从需求到方案；逆向模式是从**已有产物**反推出设计规格。

适用场景：

- 拿到截图 / 竞品 / 参考设计，想知道「为什么这样设计」
- 复刻一个喜欢的设计但要适配自己的产品
- 维护老项目但没有设计文档

流程：

1. **收集输入**：截图、Figma 链接、参考 URL、代码仓库
2. **拆解层级**：
   - 信息架构：页面分区、导航路径
   - 视觉：色彩、字体、间距、圆角、阴影
   - 组件：按钮、表单、卡片、列表、导航
   - 交互：状态、过渡、反馈
3. **量化**：用感觉层描述的话翻译成具体 token（参考核心原则）
4. **重建文档**：按本 Skill 的「输出格式」写出完整规格
5. **标注差异**：对比原参考，标注哪些可借鉴、哪些必须改

输出格式同正向设计，但每个 token 字段后加「来源：参考 X」标记。

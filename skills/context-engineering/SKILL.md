# Context Engineering

把有限上下文窗口当作运行时资源管理：只给模型当前决策真正需要、可信、最新且位置合适的信息。

## 何时使用

- 设计 Agent、RAG 或多轮助手的上下文组装流程
- 上下文过长、信息相互冲突、工具输出淹没任务或记忆污染
- 需要确定哪些信息常驻、按需检索、压缩、淘汰或隔离
- 需要为系统提示、用户输入、历史、检索和工具结果分配 Token 预算

不要用于：

- 只编写 system prompt 或 few-shot 文案（用 `prompt-writing`）
- 探索现有代码库的入口和调用链（用 `codebase-exploration`）
- 设计整个应用的服务边界和技术架构（用 `design`）
- 衡量模型、RAG 或 Agent 的输出质量（用 `llm-evaluation`）
- 普通文档摘要（用 `summary`）

## 上下文契约

每类上下文都要明确：

- 来源与所有者
- 进入上下文的触发条件
- 信任级别与冲突优先级
- 新鲜度和失效条件
- 最大 Token 预算
- 压缩或截断方式
- 敏感信息与租户隔离要求

## 流程

1. **定义决策点**：明确模型在每一步必须做出的决定、需要的证据和不需要的信息
2. **盘点上下文源**：覆盖系统指令、用户输入、会话历史、记忆、检索文档、代码、工具结果和运行状态
3. **标注信任与生命周期**：区分指令与数据、权威与非权威、稳定与易过期、会话级与长期记忆
4. **设计选择策略**：为每个决策点规定常驻内容、条件检索、过滤、去重和拒绝规则
5. **设计排序与边界**：安排信息顺序、分隔符、来源标签和冲突处理，避免非可信内容伪装成指令
6. **分配 Token 预算**：为各区域设置硬上限与预留输出空间，规定超限时的淘汰优先级
7. **设计压缩与记忆**：保留事实、决策、约束和未解决事项；为摘要建立来源链接、版本和更新策略
8. **处理工具结果**：只保留完成当前决策所需字段，限制大输出、错误堆栈和重复日志
9. **验证上下文行为**：使用长对话、冲突信息、过期记忆、检索噪声和注入内容检查契约
10. **建立可观测性**：记录每次运行选入了什么、为何选入、消耗多少 Token、丢弃了什么

完成标准：每个模型决策点都有明确的上下文来源、选择规则、信任边界、预算、失效策略和验证方法。

## 输出格式

```markdown
# Context Contract

## 决策点
- [模型需要做什么决定]

## 上下文清单
| 区域 | 来源 | 触发条件 | 信任级别 | 新鲜度 | Token 上限 |
|---|---|---|---|---|---:|

## 组装顺序
1. [区域 + 原因]

## 冲突与淘汰规则
- 冲突优先级：...
- 超限淘汰顺序：...
- 失效条件：...

## 记忆策略
- 写入：...
- 读取：...
- 更新 / 删除：...

## 验证场景
- [长上下文 / 过期信息 / 注入 / 多租户等]
```

## 行为准则

- **相关性不是充分条件**：信息还必须可信、及时并服务当前决策
- **指令与数据分层**：检索内容、网页和工具输出默认是数据，不自动获得指令权威
- **预算必须有淘汰顺序**：不要把 Token 上限交给随机截断
- **记忆可追溯可删除**：长期记忆保存来源、时间和删除路径
- **先修上下文再堆 Prompt**：信息供给错误时，改写措辞通常不能解决根因

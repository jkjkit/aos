# Incident Response

生产事故的**完整响应流程**——从发现到复盘。**不**做开发期 Bug 排查（那是 `debug`），**不**做监控告警设计（那是 `observability`），**不**做值班排班（那是 `oncall` 待加）。

## 何时使用

- 生产环境出现事故（P0 / P1 级）
- 需要启动事故响应流程
- 写 Postmortem 报告
- 设计事故响应 SOP

不要用于：

- 开发期 Bug → `debug`
- 监控告警配置 → `observability`
- 值班排班 → `oncall`（待加）
- 性能调优 → `performance`

## 流程

### 1. 定级（Severity）

| 级别 | 含义 | 响应时间 | 例子 |
|------|------|----------|------|
| **SEV-1** | 核心功能完全不可用 | 立即 | 支付失败、数据丢失 |
| **SEV-2** | 核心功能部分受损 | 30 分钟 | 关键 API 报错率 50% |
| **SEV-3** | 非核心功能受损 | 4 小时 | 报表功能报错 |
| **SEV-4** | 性能下降 / 小问题 | 24 小时 | 加载变慢 |

### 2. 启动响应

**谁参与？**

| 角色 | 职责 |
|------|------|
| **IC（Incident Commander）** | 总指挥，决定优先级，分配任务，**不亲自 debug** |
| **Ops / SRE** | 缓解（回滚 / 限流 / 切流量） |
| **开发** | 找根因 / 修代码 |
| **通信官** | 内部同步 / 客户沟通 |
| **记录员** | 实时记录时间线和决策 |

**第一句话模板（Slack / 群）：**

```
[SEV-2] 事故启动 @ 14:30
症状：核心 API 报错率从 1% 涨到 30%
影响：约 5000 用户受影响
IC: @张三
下一步：缓解中，预计 14:50 前给进展
文档：[incident 链接]
```

### 3. 缓解优先（Stop the bleeding）

**先缓解，再根因。**

缓解手段：

| 手段 | 适用场景 | 命令示例 |
|------|----------|----------|
| 回滚 | 最近发布引起 | `kubectl rollout undo` |
| 限流 | 流量过大 | 调整 rate limit |
| 切流量 | 部分服务故障 | 切到备用集群 |
| 扩容 | 资源不足 | `kubectl scale` |
| 禁用功能 | 功能故障 | feature flag 关闭 |
| 切换读 | 主库故障 | 切到从库 |

### 4. 时间线记录

**实时记录每个事件**（关键时间点）：

```
14:30 IC @张三 启动 SEV-2
14:32 Ops @李四 加入，正在回滚
14:35 回滚完成，错误率降至 5%
14:40 仍高于基线（1%），继续排查
14:50 发现根因：缓存配置错误
14:55 修复完成，错误率回归 1%
15:00 IC 宣布事故关闭，进入 Postmortem 阶段
```

### 5. 沟通

#### 内部同步

- **频率**：每 15-30 分钟一次进展更新
- **内容**：当前状态 / 下一步 / 预计恢复时间
- **不要**：技术细节长篇大论

#### 客户沟通

- **何时**：SEV-1 / SEV-2 影响用户时
- **谁**：通信官 / PR / 客服主管
- **频率**：每小时或状态变化时
- **模板**：

```
[状态更新 14:50]
我们正在处理一个影响部分用户的服务问题。
- 受影响：约 5000 用户（约总用户 5%）
- 当前状态：错误率已从 30% 降至 5%
- 预计恢复：1 小时内
- 我们的行动：[概要]

下次更新：15:30 或状态变化时
```

#### 事故关闭通知

```
[已恢复 15:05]
问题已修复，所有服务恢复正常。
- 原因：[简短说明，不甩锅]
- 修复：[做了什么]
- 影响时长：约 35 分钟
- 后续：我们会做 Postmortem，48 小时内发布

感谢您的耐心。
```

### 6. Postmortem（无指责复盘）

**核心原则：**

- ❌ 找人背锅 → ✅ 找系统漏洞
- ❌ 「谁搞坏了」 → ✅ 「为什么系统让一个人能搞坏」
- ❌ 惩罚当事人 → ✅ 改进防御

**5 Whys 分析：**

```
问题：错误率飙升至 30%
Why 1：缓存配置错误
Why 2：配置脚本有 bug
Why 3：脚本没经过 review
Why 4：发布流程没有强制 review
Why 5：没有自动检测配置变更的机制
```

**Postmortem 模板：**

```markdown
# Postmortem: <事故标题>

## 摘要
- 时间：[开始 - 结束]
- 严重级别：SEV-X
- 影响：[用户数 / 营收 / 持续时间]
- 根因：[一句话]

## 时间线
[按发生顺序列出关键事件]

## 影响
- 受影响用户：
- 营收影响：
- 数据影响：
- 品牌影响：

## 根因分析
[5 Whys 或鱼骨图]

## 检测
- 怎么发现的：[告警 / 客户反馈 / 内部发现]
- 检测延迟：[多久才发现]
- 如何更快发现：[改进]

## 响应
- 谁发现的：
- IC 是谁：
- 缓解花了多久：
- 如何更快缓解：[改进]

## 改进项（Action Items）

### 立即（本周）
- [ ] [改进 1]
- [ ] [改进 2]

### 短期（1 个月）
- [ ] [改进 3]

### 长期（季度）
- [ ] [改进 4]

## 学到的教训
- [教训 1]
- [教训 2]

## 相关链接
- 时间线：[]
- 告警：[]
- 代码：[]
```

## Hard Rules

### 禁止：找人背锅

```
❌ 「是 @张三 改坏了」
✅ 「为什么系统允许一个人改动就引发事故」
```

### 禁止：技术细节长篇大论给客户

```
❌ 「Our Redis cluster had a cache stampede due to...」
✅ 「我们遇到了技术问题，正在修复」
```

### 禁止：隐瞒影响

```
❌ 「小问题，没影响」
✅ 「约 5000 用户受影响，我们正在处理」
```

### 禁止：IC 亲自 debug

```
❌ IC 既指挥又修代码
✅ IC 只指挥，debug 交给开发
```

### 禁止：跳过 Postmortem

```
❌ 「问题修好了，就这样吧」
✅ 「48 小时内 Postmortem，下次避免重蹈覆辙」
```

## 行为准则

- **缓解优先于根因**
- **沟通频次固定**：每 15-30 分钟
- **事实先行**：不要猜测、不要粉饰
- **无指责文化**：找系统漏洞，不找人
- **记录先行**：Postmortem 必须在事故关闭后 48 小时内完成

## 与其它 Skill 的协作

| Skill | 关系 |
|---|---|
| `debug` | 上下游：找根因时用 debug |
| `observability` | 上下游：检测依赖监控告警 |
| `risk-analysis` | 上下游：复盘用 risk-analysis 找系统风险 |
| `changelog` | 下游：事故修复入 changelog |

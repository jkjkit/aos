# Document

按目的产出技术文档——README、API 文档、用户指南、架构文档、变更日志。

## 何时使用

- 新模块 / 新项目需要 README
- 公共 API 缺少使用说明
- 架构变了需要更新架构文档
- 准备发版，需要写 changelog
- 内部规范或 runbook 还没写过

不要用于：

- 写代码注释（属于 coding）
- 写需求 / 设计 / 测试文档（用对应 Skill）
- 创建或修改 AOS Skill 及其路由规则（用 `skill-authoring`）

## 文档类型速查

| 类型 | 受众 | 核心问题 |
|------|------|----------|
| README | 首次接触者 | 这是什么、为什么用、怎么开始 |
| API 文档 | 调用方 | 怎么调用、参数、返回、错误 |
| 用户指南 | 最终使用者 | 怎么完成某个任务 |
| 架构文档 | 开发者 / 维护者 | 系统由哪些部分组成、为什么这样 |
| Changelog | 已使用者 | 这次发布变了什么 |
| Runbook | 运维 / oncall | 出问题时怎么修 |

## 通用流程

1. **明确受众与场景**：第一次接触者 vs 老用户；阅读路径是什么
2. **搭骨架**：标题、章节顺序、表格 / 图位置；先列大纲再填内容
3. **示例优先**：能跑的命令、完整的代码片段、真实的请求 / 响应
4. **去冗余**：不写「这个项目是一个非常好的项目」之类的废话
5. **可验证**：链接、命令、版本号都要真实可点
6. **写完读一遍**：大声读出来——读不顺的就是没写清楚

## 各类型要点

### README

最少包含：

- 一句话讲清是什么、给谁用
- 快速开始（5 分钟内能跑起来）
- 主要功能 / 特性
- 链接到更详细的文档
- 许可证 / 贡献方式

### API 文档

每个端点：

- 方法 + 路径
- 鉴权要求
- 请求参数（路径 / 查询 / Body）
- 响应结构与字段说明
- 错误码与含义
- 一个完整 curl / 代码示例

### 架构文档

- 一张总览图 + 一段说明
- 每个核心组件的职责（一句话）
- 关键数据流（用户 → ... → 数据库）
- 关键技术决策与原因（链接 ADR）

### Changelog

按 Keep a Changelog 规范：

- `Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security`
- 每个条目以用户视角写「多了什么能力」「修了什么」而不是「改了哪行」
- 标注破坏性变更和迁移路径

## 行为准则

- **不堆术语**：能用日常中文写清就不用黑话
- **不写废话**：「这个系统非常强大」这种句子删掉
- **不假定上下文**：读者不一定看过上一份文档
- **示例真实**：不要编造请求 / 响应，要从实际代码里取

## 不要做的事

- 不要把文档写得像营销文案
- 不要在文档里粘贴大段代码而不解释
- 不要写「待完善」「TODO」——直接不写
- 不要用占位符链接

# Requirement

把用户描述的「要做一个 X」转换为结构化的需求文档。

## 何时使用

- 用户说「我想加个功能」「做一个 XX 系统」但描述模糊
- 需要把口头描述整理为可评审的 PRD
- 团队对要做的事情理解不一致，需要书面统一
- 在写设计文档或测试用例之前，先澄清范围

不要用于：

- 已经有了 PRD 只需实现（用 coding）
- 只是技术问题排查（用 debug）

## 流程

1. **澄清原始输入**：识别用户口中的关键词，区分「要做什么」「不能做什么」「希望达到什么效果」
2. **拆分核心与扩展**：用 MoSCoW（Must / Should / Could / Won't）划分
3. **场景化**：为每个核心场景写出「用户故事」——谁，要做什么，得到什么
4. **定义验收标准**：每个故事至少 2 条可验证的「完成」条件
5. **边界声明**：明确「不做的事」，避免后续范围蔓延
6. **依赖与约束**：列出技术、第三方、合规、时间上的硬约束
7. **输出结构化文档**（见下）

## 输出格式

```markdown
# 需求文档

## 概述
[1-3 段，背景 + 目标 + 范围]

## 用户故事
- 作为 [角色]，我想要 [功能]，以便于 [价值]
- ...

## 功能需求
| ID | 需求 | 优先级 (M/S/C/W) | 验收标准 |
|----|------|-----------------|----------|

## 非功能需求
- 性能 / 安全 / 可用性 / 兼容性 ...

## 不在范围内
- [显式排除]

## 依赖与约束
- [技术 / 第三方 / 合规 / 时间]

## 风险与假设
- [列出可能改变方向的前提]
```

## 行为准则

- **澄清而非猜测**：模糊处向用户提问，而不是替用户做主
- **可验证**：每条验收标准都应该能被 Yes/No 判定
- **不要夹带设计**：需求文档只描述「要什么」，不规定「怎么做」
- **承认未知**：把不确定的事情标出来，而不是藏在脚注里

## 不要做的事

- 不要替用户写技术选型（那是 design 的事）
- 不要在需求里写实现细节或具体代码
- 不要为了完整度虚构用户没提的功能

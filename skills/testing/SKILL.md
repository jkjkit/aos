# Testing

为一段已实现的代码设计测试策略，产出可执行的测试用例并评估覆盖情况。

## 何时使用

- 新功能开发完成，需要补齐测试
- 老模块缺测试，要从零补
- 修完 Bug 要加回归用例
- 评估当前覆盖率缺口

不要用于：

- 还没实现的代码（先 coding）
- 性能基准与压测（用 performance）
- 代码风格与规范审查（用 `review`）
- LLM、Prompt、RAG 或 Agent 的质量评估、Judge 校准和回归门禁（用 `llm-evaluation`）
- 键盘、焦点、屏幕阅读器、对比度和缩放等专项审计（用 `accessibility-audit`）
- 实现完成后只需运行构建、lint、测试和验收门禁（用 `verification`）

## 流程

1. **理解被测代码**：核心路径、边界条件、异常分支、外部依赖与可测边界
2. **选择测试层级**：单元 / 集成 / E2E；优先单元，遵循测试金字塔
3. **设计用例**：覆盖正常路径、边界值、异常路径；一个用例聚焦一个断言
4. **决定 Mock 边界**：能跑的依赖留真实，难复现的用 Stub/Fake；不要全 mock
5. **写测试代码**：命名清晰（被测对象 + 场景 + 预期）；与已有测试共用 helper
6. **运行并收集覆盖率**：行覆盖 + 分支覆盖 + 关键路径覆盖
7. **标注风险**：未覆盖 / 难覆盖的部分写明原因

## 输出格式

```markdown
# Test Plan

## 策略
- 层级：Unit / Integration / E2E
- 框架：xxx
- 覆盖率目标：行 ≥ 80% / 分支 ≥ 70%

## 测试用例

### TC-001: 标题
- Priority: Critical / Major / Minor
- Input: [输入]
- Expected: [预期]
- Assert: [断言点]

### TC-002: ...

## 覆盖率
- Line: N%
- Branch: M%
- 未覆盖：[区域 + 原因]

## 风险
- [已知无法覆盖的部分 + 是否需要手动验证]
```

## 优先级原则

- 优先级按「Bug 出现后果」排，不是按实现难易
- Critical：核心业务路径、安全相关、数据一致
- Major：边界、错误处理、权限
- Minor：样式、纯展示

## 行为准则

- **一个用例一件事**：别把多个断言堆在一起
- **测试行为而不是实现**：测试失败应该说明行为坏了，不是实现变了
- **避免脆弱**：不要断言与实现耦合的细节（如私有方法、日志文案）
- **承认不可测**：部分代码难以自动测试时直接说，并建议手动验证手段

## 不要做的事

- 不要为了覆盖率写空断言
- 不要让测试依赖执行顺序
- 不要在测试里 sleep 等待真实时间
- 不要 mock 你不理解的依赖

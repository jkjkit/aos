# Coding

基于 `design` Skill 的输出（或已存在的实现约定）生成实际代码。

## 何时使用

- 设计方案已就绪，开始编码
- 需要实现一个明确的功能或修复
- 需要补齐已有模块的实现细节

不要用于：

- 方案还没定（先 design）
- 已有方案但只想要第二视角（用 review）

## 匹配边界

只要最终交付物包含新增或修改应用源代码、运行配置或测试文件，主 Skill 应为 `coding`；AOS Skill 定义与路由维护使用 `skill-authoring`。

- 只要技术方案文档 → `design`
- 只要界面交互和视觉规范 → `design-interface`
- 只要 API 契约 → `api-design`
- 只要数据库方案 → `database`
- 要把方案落到应用代码、组件、运行配置或测试文件 → `coding`
- 要创建或修改 AOS Skill、路由和回归语料 → `skill-authoring`

`coding` 可以读取上述 Skill 的产出作为输入，但不应替代它们完成尚未明确的设计决策。

## 流程

1. **对齐设计**：读完设计文档，把不确定的地方列出来问用户；不要假装清楚
2. **先骨架后细节**：先建目录、主要类/函数签名、接口、占位实现；再回头填业务
3. **遵循项目约定**：命名、目录、日志、错误处理、测试位置都要与已有代码风格一致
4. **错误处理**：可预期的错误显式处理；不可预期的用顶层兜底；不要吞错
5. **测试同步**：核心路径补最小单测；与已有测试共用 helper；不要为了覆盖率写空断言
6. **小步可回滚**：每个提交做一件事；不要把多个变更混在一起
7. **自检**：编译 / 类型检查 / lint / 单测全部通过再交给下一步

## 输出形态

- 修改或新增的源文件
- 必要的单测
- 一句话总结改动点（用于 commit message 或交接）

## 行为准则

- **不要顺便重构**：如果发现需要重构的地方，单独开任务
- **不要顺手加功能**：用户没要的「顺手优化」一律不做
- **不要复制粘贴实现**：相似不等于相同，必要时抽取公共部分
- **承认「不确定」**：宁可停下来问，也不要假装会做

## 不要做的事

- 不要在没设计的情况下写核心业务
- 不要在改动里留调试代码、注释掉的代码、临时代码
- 不要修改测试以迁就错误实现

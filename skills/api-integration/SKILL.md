# API Integration

对接外部 API（支付、短信、地图、AI 服务等）的标准化做法——客户端封装、超时、降级、监控。

## 何时使用

- 首次接入第三方 API
- 现有第三方对接混乱，需要重整
- 准备增加新的第三方服务
- 第三方服务稳定性问题频发

不要用于：

- 设计自己系统的 API（用 `api-design`）
- 单次 PoC 验证（直接做）

## 与「api-design」的区别

| 维度 | api-design | api-integration |
|------|-----------|----------------|
| 视角 | 我们提供 API | 我们调用别人的 API |
| 关注点 | 契约、字段、版本 | 客户端封装、稳定性、降级 |
| 产物 | OpenAPI / Schema | 客户端 SDK + 配置 + 监控 |

## 流程

### 1. 评估第三方

接入前先调研：

- **稳定性**：历史可用性 SLA；近 3 个月事故
- **文档质量**：OpenAPI / SDK 是否齐全；示例代码可不可跑
- **限流策略**：每秒请求数、每日配额
- **定价**：按调用 / 包月 / 阶梯
- **合规**：数据出境、隐私、合同条款
- **退路**：服务挂了能切到谁；能不能自实现

### 2. 客户端封装

永远不要在业务代码里直接调用第三方 SDK。封装一层：

- **接口隔离**：业务只看到接口，不知道 SDK 存在
- **配置外置**：endpoint / key / 超时都从配置读
- **可替换**：换 SDK 只改实现层

```python
# 业务层看到的接口
class PaymentClient(Protocol):
    def charge(self, order_id: str, amount: int) -> ChargeResult: ...

# 实现层（具体 SDK 细节藏在这里）
class StripePaymentClient:
    def __init__(self, api_key: str, timeout: int = 5): ...
    def charge(self, order_id, amount): ...
```

### 3. 超时与重试

- **必设超时**：connect / read / total 都要设
- **分级超时**：核心路径 < 1s；非关键可放宽
- **幂等才重试**：POST 不带 Idempotency-Key 不要重试
- **退避策略**：指数退避 + 抖动；最多 3 次
- **熔断**：连续失败达到阈值，跳过调用直接降级

### 4. 错误处理

| 错误类型 | 处理 |
|----------|------|
| 4xx 客户端错误 | 不要重试；记录；返回明确错误码 |
| 5xx 服务端错误 | 重试 + 降级 |
| 超时 | 重试 + 降级 |
| 网络断开 | 重试 + 降级 |
| 限流（429） | 等待 Retry-After 后重试 |
| 配额用尽 | 立即降级 + 报警 |

### 5. 降级策略

每种第三方调用都要有降级路径：

- 支付失败 → 排队重试 + 用户告知
- 短信失败 → 重试 + 备用通道
- 地图 API 失败 → 用本地缓存坐标
- AI 推理失败 → 兜底文案 / 队列延迟处理

### 6. 监控

- 调用量（按接口 / 按状态码）
- 错误率（区分 4xx / 5xx / 超时）
- 延迟（P50 / P95 / P99）
- 配额消耗（每日 / 每月）
- 降级触发次数
- 第三方状态页订阅

### 7. 安全

- **密钥管理**：环境变量 / 密钥管理服务，不入库
- **最小权限**：申请的 API 权限按需勾选
- **数据脱敏**：日志里不打印完整请求 / 响应体
- **回调验签**：第三方回调必须验签 + 防重放

## 行为准则

- **永远封装一层**：业务代码不直接依赖第三方 SDK
- **超时先于重试**：没超时的重试只会放大故障
- **降级是必选项**：不允许「第三方挂了我们就挂了」
- **监控从第一天开始**：上线后才知道「没监控」= 永远不知道
- **密钥不入库**：哪怕只是测试 key

## 不要做的事

- 不要把 API key 写进代码
- 不要在循环里串行调用第三方（用批量接口或并发）
- 不要假设第三方 100% 可用
- 不要忽略 429 限流响应
- 不要让第三方异常直接冒泡到用户

# Roadmap

把一段时期（季度 / 半年 / 一年）要做的事排成路线图，标注优先级、依赖、取舍与重估触发条件。

## 何时使用

- 季度 / 半年规划会议
- 向管理层或客户解释技术投入
- 团队方向调整，需要书面同步
- 资源（人 / 钱）需要提前评估

不要用于：

- 当前迭代的具体任务（用 `task`）
- 单个功能的设计（用 `design`）
- 单次会议的纪要（用 `meeting-notes`）

## 核心原则：路线图是承诺，不是愿望清单

> 路线图要做的事必须能在合理时间内完成；想做但来不及的，要么砍掉、要么挪到下一期。

一份好的路线图：

- 有明确的「不做什么」
- 有可衡量的成功指标
- 有清晰的优先级与依赖
- 标注不确定性，承诺可重估

## 流程

1. **明确范围与周期**：本路线图覆盖哪几个月；谁的目标（团队 / 产品 / 公司）
2. **回顾上一期**：上一期路线图完成度、未完成原因、经验教训
3. **收集输入**：
   - 用户需求与痛点
   - 技术债清单
   - 业务 KPI 与增长目标
   - 竞争 / 市场变化
   - 团队能力与容量
4. **设定主题**：把零散的想法归到 3-5 个主题（如「稳定性」「性能」「新能力 A」「技术债偿还」）
5. **纳入与排除**：明确这期做什么、不做什么；为什么排除
6. **排定里程碑**：把主题落到月度 / 双周里程碑
7. **标注依赖**：哪些事依赖外部资源（招人、跨团队、上游决策）
8. **定义成功指标**：每个主题至少 1 个可衡量指标
9. **风险与重估触发条件**：什么情况下路线图需要重排
10. **沟通与对齐**：向团队、上级、跨团队同步

## 输出格式

```markdown
# Roadmap：2026 Q3 - Q4

## 愿景
[半年内我们要成为什么样的系统 / 团队]

## 主题

### 稳定性
- 目标：核心服务可用性 99.9% → 99.95%
- 关键工作：
  - 全链路 tracing 接入
  - 数据库主从切换演练
  - 关键路径 SLO 制定
- 成功指标：错误率 < 0.1%，P99 延迟 < 500ms

### 新能力：实时数据看板
- 目标：业务侧自助查询核心指标
- 关键工作：
  - 数据流 CDC 接入
  - 查询引擎选型
  - 看板原型
- 成功指标：业务自助查询覆盖率 > 60%

### 技术债：订单模块重构
- 目标：可维护性提升
- 关键工作：[详见内部 RFC-042]
- 成功指标：新功能交付周期缩短 30%

## 不做什么
- ❌ 多语言支持（资源不足，下期评估）
- ❌ 移动端原生重写（先用 H5 验证）

## 里程碑
| 时间 | 节点 |
|------|------|
| 7 月底 | tracing 全量接入 |
| 8 月底 | 数据库切换演练 |
| 9 月底 | 看板 MVP 上线 |
| 10 月底 | 订单重构第一阶段 |
| 11 月底 | SLO 全量上线 |
| 12 月底 | 复盘 + 下期路线图 |

## 依赖与资源
- 招 1 名 SRE（7 月到位）
- 需要 DBA 协助 30 人天（已申请）
- 上游 SDK 升级由平台团队负责（Q3 内）

## 重估触发条件
- 业务量超过预期 50%：性能优化优先级上调
- 重大事故：稳定性优先，其他延后
- 团队关键人员变动：重排容量

## 与上一期的对比
- 完成率：上一期 70%（10/14 项）
- 推迟：[A、B]
- 取消：[C，原因]
```

## 行为准则

- **承诺可兑现**：路线图是承诺，不是 dream list
- **不做什么更重要**：明确排除项比罗列要做的事更难
- **里程碑可验证**：每条都能在节点上判定完成或未完成
- **承认不确定性**：技术探索类工作给「尝试 + 重评」空间
- **沟通 > 文档**：路线图是讨论的起点，不是终点

## 不要做的事

- 不要把单个任务当路线图项目（粒度太细）
- 不要承诺超过团队容量 80% 的工作（留 buffer）
- 不要忽略「不做什么」
- 不要写一份永远不变的路线图
- 不要让路线图成为「每个领导都要加一条」的大杂烩

## 与其它 Skill 的协作

- 主题落地 → 用 `task` 拆为迭代任务
- 主题需要新能力 → 用 `requirement` + `design`
- 主题涉及架构调整 → 用 `migration`
- 主题评审会议 → 用 `meeting-notes` 记录

# Task

把一个目标（需求、问题、特性）拆解为可独立交付的任务，标注依赖与优先级。

## 何时使用

- 收到一个范围较大的需求，要分给多人 / 多个阶段
- Sprint 计划，要从一堆想法里挑出本轮做什么
- 需要估算总工作量（小时 / 人天）
- 需要可视化依赖关系（哪些可以并行、哪些必须串行）

不要用于：

- 单人一天能做完的小改动（直接做）
- 已经拆好只需要记录（用 changelog）

## 流程

1. **明确目标与边界**：引用需求文档或一句话讲清
2. **做 WBS 分解**：把目标拆成 3-7 个阶段，每个阶段再拆成 2-5 个任务
3. **写任务卡片**：每张卡片包含标题、描述、验收标准、估算、依赖
4. **排优先级**：MoSCoW 或 P0/P1/P2；先排「解锁其它任务」的
5. **标依赖关系**：用图或表格说明谁阻塞谁
6. **分配 / 跟进**：标负责人、状态（todo / doing / review / done）

## 输出格式

```markdown
# 任务分解

## 目标
[一句话]

## 阶段

### 阶段 1：[阶段名]
| ID | 任务 | 估算 | 依赖 | 负责人 | 状态 |
|----|------|------|------|--------|------|

### 阶段 2：...

## 依赖图
```
A → B → C
     ↘ D
```

## 本轮（推荐先做）
- [ ] ...
- [ ] ...
```

## 估算方法

- **T-Shirt Size**：XS / S / M / L / XL（适合初步排期）
- **Story Points**：1, 2, 3, 5, 8, 13（适合敏捷团队）
- **小时 / 人天**：适合对外承诺

不要在分解阶段做精确到「3.5 小时」的估算——粒度太细反而失真。

## 行为准则

- **每条任务可独立完成**：不应有「其他任务完成 80% 才能开始」这种描述
- **每条任务可独立验证**：验收标准要可被 Yes/No 判定
- **任务粒度均匀**：不要混进「写一个完整登录系统」和「改一行文案」
- **承认未知**：标「需要进一步澄清」而不是硬猜

## 不要做的事

- 不要把任务拆得过细（< 1 小时）——管理成本超过执行成本
- 不要把多个不相关的改动合成一条任务
- 不要在没有验收标准的情况下输出任务列表

# Risk Analysis

系统性识别一个项目 / 决策 / 变更的**所有相关风险**，评估概率与影响，输出可执行的缓解措施与应急预案。

**与 `design` 的区别：** `design` 关注「怎么做」（架构、接口、数据），风险识别是其中一节；`risk-analysis` 关注「哪里会出错」，覆盖**技术之外的业务、合规、运营、财务**等所有维度。

## 何时使用

- 启动新项目 / 新功能前的风险评估
- 重大架构变更（迁移、重写、平台切换）
- 涉及第三方依赖、敏感数据、合规要求
- 准备发布前的 Go/No-Go 决策
- 周期性风险复盘

不要用于：

- 单个 Bug 的修复（用 `debug`）
- 安全漏洞扫描（用 `security`）
- 性能问题分析（用 `performance`）
- 个人信息生命周期、最小化、同意、保留、删除和共享的专项审查（用 `privacy-review`）

## 风险维度

按 6 个维度全面识别，避免遗漏：

| 维度 | 关注点 | 典型问题 |
|---|---|---|
| **技术** | 架构、依赖、性能、安全、数据 | 第三方库不再维护？性能瓶颈？单点故障？ |
| **业务** | 市场、用户、收入、增长 | 用户真会买账吗？竞品反应？收入假设？ |
| **合规** | 法律、隐私、监管、行业标准 | GDPR？数据出境？行业准入？ |
| **运营** | 人员、流程、工具、运维 | 关键人员离职？值班没人？备份恢复演练？ |
| **财务** | 成本、收入、汇率、税务 | 云成本失控？汇率波动？退款率？ |
| **时间** | 工期、依赖、关键路径 | 延期概率？上游阻塞？旺季冲突？ |

每个维度都要主动询问「最坏情况」。

## 流程

### 1. 锚定对象

明确分析什么：

- 项目 / 功能 / 变更的名称
- 范围（多大）
- 时间窗口（什么时候的风险？上线前？上线后半年？）
- 关键假设（业务 / 技术 / 用户）

### 2. 风险识别

按维度逐项扫描。技巧：

- **5 Why 追问**：每个风险问 5 次「为什么」
- **最坏情况**：每个维度主动想最坏情形
- **历史教训**：过去类似项目踩过什么坑
- **未知未知**：列出「我们现在没想到的风险」作为 placeholder

### 3. 评估

每个风险评估：

| 字段 | 说明 |
|---|---|
| **概率** | Low / Medium / High |
| **影响** | Low / Medium / High / Critical |
| **优先级** | 概率 × 影响（用矩阵） |
| **触发条件** | 什么情况下会发生 |
| **可检测性** | 发生时能否及时发现 |

### 4. 缓解措施

每个 High / Critical 风险必须有：

- **预防**：降低发生概率
- **检测**：发生时及时发现
- **响应**：发生后的具体动作
- **回滚 / 备用方案**：最坏情况下的 Plan B

### 5. 风险登记册

把所有风险汇总成可追踪的清单：

```
| ID | 风险 | 维度 | 概率 | 影响 | 优先级 | 负责人 | 状态 |
|----|------|------|------|------|--------|--------|------|
```

### 6. 输出格式

```markdown
# Risk Analysis: <对象>

## 范围与假设
- 分析对象：
- 时间窗口：
- 关键假设：

## 风险登记

### 技术风险

#### R-T01: 第三方库不再维护
- 概率：Medium
- 影响：High
- 优先级：P1
- 触发条件：库 < 1 年无发布；安全漏洞未修复
- 缓解：
  - 预防：选 lib 前看 GitHub 活跃度
  - 检测：Dependabot 自动告警
  - 响应：评估替代库
  - 回滚：自实现核心功能（已评估可行性）

#### R-T02: ...

### 业务风险

### 合规风险

### 运营风险

### 财务风险

### 时间风险

## Top 5 风险
1. R-X01（原因）
2. ...

## 应急预案

### 触发场景 1：[什么情况]
- 第一步：[动作]
- 第二步：[动作]
- 负责人：

### 触发场景 2：...

## 风险回顾
- 下次 review 日期：
- 已关闭的风险：
- 新增的风险：
```

## 风险矩阵

```
影响 ↑
Critical │  M  │  H  │  C  │
High     │  L  │  M  │  H  │
Medium   │  L  │  L  │  M  │
Low      │  L  │  L  │  L  │
         └────┴────┴────┘
           Low  Med  High → 概率
```

- **C** = Critical：必须立即处理
- **H** = High：项目开始前必须有缓解方案
- **M** = Medium：列入下个迭代处理
- **L** = Low：记录并监控

## Hard Rules

### 禁止：只识别已知风险

```
❌ 列 5 个明显的风险就交差
✅ 主动问「我们没想到的风险是什么」
```

### 禁止：没有缓解措施的高风险

```
❌ 列出 High 风险但不写怎么应对
✅ 每个 High/Critical 都要有预防 + 检测 + 响应 + 回滚
```

### 禁止：用形容词代替具体评估

```
❌ 风险很大 / 风险较小
✅ 概率 Medium，影响 High，优先级 P1
```

### 禁止：忽略「已知未知」

```
❌ 假装所有风险都已识别
✅ 明确标注「这个维度我们目前信息不足，建议后续补充」
```

### 禁止：风险没有负责人

```
❌ 列了风险但没人管
✅ 每条风险必须有 owner
```

## 行为准则

- **系统性 > 经验性**：不要只挑你熟悉的风险，每个维度都要过
- **量化 > 描述**：用概率 × 影响矩阵，不用「可能」「大概」
- **可执行 > 全面**：每个风险都要有可执行的下一步
- **承认无知**：列出「我们没识别到的风险」是诚实
- **持续更新**：风险登记册是活文档，不是一次性

## 不要做的事

- 不要把所有风险都列成 High（失去优先级）
- 不要给没有负责人的风险
- 不要把缓解措施写成「加强关注」「持续优化」（不可执行）
- 不要忽略合规与财务（只盯技术）
- 不要承诺 0 风险（不可能；要承诺管理）

## 与其它 Skill 的协作

| Skill | 关系 |
|---|---|
| `design` | 上游：先有架构 / 方案，再做风险评估 |
| `requirement` | 上游：先明确范围与假设 |
| `decision` | 下游：风险评估辅助 Go/No-Go 决策 |
| `security` | 并行：技术风险中的安全部分可让 security 深入 |
| `performance` | 并行：技术风险中的性能部分可让 performance 深入 |
| `review` | 并行：实施前 review 风险登记是否完整 |

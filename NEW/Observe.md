# Observe — 项目结构摸底与事实快照规范

## 1. 目标与边界（Goal & Non-Goals）

- **核心目标（Goal）**：以最小上下文开销，快速建立目标项目或指定模块的客观事实快照（技术栈、目录职责、核心调用链、运行方式及现存异常）。
- **非目标（Non-Goals）**：
  - 只做客观事实采集与结构还原，不输出主观优劣评判或重构方案（方案评估与优化移交 `Analyze`）。
  - 严禁修改任何源码、配置或安装依赖（代码实现移交 `Coding`）。
  - 严禁读取 `.env*` 等凭证文件，严禁擅自启动运行服务。

## 2. 判定准则与负向约束（Rules & Constraints）

- **三级漏斗按需读取**：遵循「根配置与文档 $\rightarrow$ 入口与路由 $\rightarrow$ 核心业务模块」由表及里渐进读取（禁止一上来使用全盘递归读取或遍历所有源码文件撑爆上下文）。
- **噪音目录强制过滤**：执行目录扫描或搜索时，必须排除 `.git/`、`node_modules/`、`.next/`、`dist/`、`build/`、`temp/`、缓存目录及各类包管理锁文件（如 `package-lock.json`、`pnpm-lock.yaml`）。
- **事实与推论严格分离**：所有架构与链路结论必须标注真实文件路径及关键符号（如 `src/server/index.ts:createApp`）；未实际读取验证的深层分支必须显式标注 `[待验证]`（禁止凭文件名或目录名臆测内部实现）。

## 3. 执行流程与门禁（Workflow & Gates）

### Step 1：宏观定界（Level 1 — 根配置与文档层）
1. 列出项目根目录顶层结构。
2. 按序优先读取：`AGENTS.md` / `HANDOFF.md`（若存在） $\rightarrow$ `README.md` $\rightarrow$ 包管理与构建配置（`package.json`、`tsconfig.json`、`pyproject.toml`、`Cargo.toml` 等） $\rightarrow$ 启停脚本（`start.*` / `stop.*`）。
3. 提取技术栈、外部依赖、模块划分与原生脚本命令。

### Step 2：主干追踪（Level 2 — 入口与数据契约层）
1. 定位并读取应用启动入口（如 `main.ts`、`app/layout.tsx`、`index.py`）、路由注册表及全局状态/配置定义。
2. 定位数据模型定义（数据库 Schema、核心接口类型 `types/`），理清核心数据结构的输入与输出。

### Step 3：局部深潜与范围门禁（Level 3 Gate）
1. 若用户指定了具体功能或问题模块，仅针对该模块的上下游调用链深入读取源码。
2. **控制门禁（Gate）**：若用户仅要求“看一下这个项目”且项目包含多个大型子系统，完成 Step 1~2 后立即输出全局概览快照，并列出子模块清单询问用户需深潜的目标，不盲目展开全部业务代码。

## 4. 输出格式规范（Output Schema）

摸底结果统一按以下 5 个标准板块输出（保持高密度列表，拒绝冗长叙述）：

### 1. 项目定位与技术底座
- **核心定位**：单句概括项目解决的核心业务问题与形态（CLI / Web 全栈 / 桌面端 / 服务库）。
- **技术栈清单**：按 `运行时与框架`、`数据存储/状态`、`关键第三方依赖`、`构建与测试工具` 分类列举。

### 2. 核心目录职责树
```text
<project-root>/
├── <dir-or-file>   # 单行说明其核心职责与边界
└── ...             # 仅保留主干结构，省略非关键叶子文件
```

### 3. 核心运行与数据链路
- **启动链路**：`入口文件:函数` $\rightarrow$ `初始化模块` $\rightarrow$ `监听/挂载点`
- **主业务流**：按核心场景列出 `请求/触发入口` $\rightarrow$ `核心处理模块 (文件路径:符号)` $\rightarrow$ `数据读写/外部调用`

### 4. 启停与验证方式
- 列出从配置或脚本中提取的标准启动、构建、检查命令（注明由用户管控或需前置条件）。

### 5. 客观异常与待确认项
- 如实列出摸底中观察到的客观问题（如：文档描述与实际代码结构不符、残留废弃目录、关键脚本缺失等）；若无异常则标注“未发现显式结构异常”。

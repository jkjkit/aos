# Coding — 代码实现与可观测性工程规范

## 1. 目标与边界（Goal & Non-Goals）

- **核心目标（Goal）**：以最小改动面交付结构清晰、逻辑自明、高度可观测且与既有代码库风格无缝融合的高质量代码。
- **非目标（Non-Goals）**：
  - 方案未对齐或根因未查明前，不盲目动笔写代码（前置评估移交 `Analyze`，未知项目摸底移交 `Observe`）。
  - 涉及视图层交互与样式布局时，必须同时受 `UIUX` 约束。
  - 默认不自动运行长期驻留服务（`dev / start`）或自动提交版本（`git commit`）。

## 2. 判定准则与负向约束（Rules & Constraints）

### 2.1 结构清晰度与最小范围准则
- **融入既有架构**：动笔前必须对齐目标项目的目录约定、命名风格、错误处理范式与已有工具函数（禁止无故引入新依赖或另起炉灶发明新范式）。
- **最小冲击与职责单一**：
  - 严格限制在已获批的文件边界内修改，**禁止顺手重构或格式化无关代码**（发现其他模块的坏味道仅在反馈中汇报）。
  - 保持单文件、单函数职责单一；通过**卫语句（Early Return）**消除深层嵌套（控制流嵌套原则上不超过 3 层）。
- **拒绝过度工程**：只为当前明确的需求编写代码，不预留无实际调用方的抽象层、泛化包装或配置开关。

### 2.2 代码可观测性硬约束（Observability）
代码必须保证在运行期与排障期“状态透明、错误可追”：
- **严禁静默吞错**：禁止出现空的 `catch {}` 块或无日志降级。所有异常捕获必须要么向上抛出带上下文的错误，要么记录包含**「失败动作 + 关键输入标识（脱敏后） + 原始错误原因」**的明确错误信息。
- **边界与契约显式化**：模块入口、外部接口调用（API / 数据库 / 文件 IO）必须对非法输入或异常返回做显式校验与快速失败（Fail-Fast），防止脏数据深入内部调用链导致难以定位的隐蔽崩溃。
- **核心流转可追踪**：复杂的状态机切换、异步任务分发或批处理关键节点，应保留精炼且结构一致的状态标识或日志锚点，确保出问题时能一眼定位卡在哪个阶段。

### 2.3 注释与整洁度铁律
- **注释只写 Why，不写 What**：
  - 代码本身应通过准确的变量与函数命名实现自解释，**严禁为显而易见的代码逻辑编写复述性注释**。
  - 仅在以下 3 种场景编写精炼注释：① **特殊的业务规则或历史兼容原因**；② **反直觉的性能优化或避坑处理（Workaround）**；③ **对外暴露的核心公共接口契约**。
- **零僵尸代码**：废弃逻辑直接删除（历史记录由 Git 保障），严禁在源码中残留大段注释掉的旧代码块、调试用的临时 `console.log / print` 或无主 `TODO`。

## 3. 执行流程与门禁（Workflow & Gates）

### Step 1：上下文与依赖对齐
1. 读取待修改文件及其直接上下游调用方，确认接口签名、类型定义与副作用范围。
2. 若属于 Bug 修复，必须先定位精确触发路径与根因，拒绝靠猜测做防御性修补（Shotgun Debugging）。

### Step 2：受控编码与静态自检
1. 执行最小化精准编辑（优先使用局部替换而非全文件覆写）。
2. 检查修改后是否引入语法错误、类型断裂、未使用的导入（Unused Imports）或违反零抖动/可观测性准则的代码。

### Step 3：熔断与验收移交门禁（Gate）
- **控制门禁（Gate）**：
  1. **三次熔断**：若同一修复或实现方向连续尝试 **3 次** 未达预期，立即停止编码，回滚或保留干净现场，向用户汇报失败根因与备选路径。
  2. **验收交接**：代码编写完成后，不擅自代用户启动生产/开发构建，必须输出清晰的**验收步骤与预期观测结果**交由用户验证。

## 4. 输出格式规范（Output Schema）

代码实现完成后，统一按以下结构交付：

### 1. 改动摘要与文件清单
- 按 `文件路径 -> 改动性质（新增/修改/删除） -> 核心逻辑说明（单句话）` 列出全部变更。

### 2. 关键实现与可观测性说明
- 简述核心逻辑的边界处理方式、异常捕获/日志锚点设计（若仅有简单修改可合并至上一项）。

### 3. 验收标准与验证步骤
- 给出供用户直接执行的 1~3 步具体操作及预期表现（如：触发某操作应看到何种响应、异常输入下应返回何种提示）。

### 4. 顺带观察到的潜在问题（如有）
- 如实列出编码过程中发现但未擅自修改的无关模块隐患（标注 `文件路径:行号`），无则省略。

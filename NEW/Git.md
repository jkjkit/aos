# Git — 版本控制与变更治理规范

## 1. 目标与边界（Goal & Non-Goals）

- **核心目标（Goal）**：确保每一次版本记录清晰、原子化、零敏感信息与零临时废料混入，并在处理分支合并或历史追溯时保持仓库状态绝对安全。
- **非目标（Non-Goals）**：
  - 只读类命令（`git status / diff / log / show / branch`）可直接执行以采集事实。
  - 变更仓库状态的写操作（`git commit / push / pull / merge / rebase / reset / checkout -f`）**必须获得用户的明确指令或授权后方可执行**。

## 2. 判定准则与负向约束（Rules & Constraints）

### 2.1 暂存前防污染核验（Pre-Stage Gate）
在规划提交或执行 `git add` 前，必须对工作区变更进行防污染过滤，**严禁使用无脑 `git add .` 或 `git add -A` 直接一把梭提交**：
- **敏感凭证阻断**：严禁暂存 `.env*`、私钥证书、含明文密钥/Token/个人隐私数据的配置文件或测试脚本。
- **临时与构建产物阻断**：严禁暂存 `temp/`、构建输出（`.next/`、`dist/`、`build/`）、依赖目录（`node_modules/`）、日志文件（`*.log`）及编辑器本地缓存。若发现 `.gitignore` 漏配上述规则，优先提醒补齐 `.gitignore`。
- **调试残留检查**：快速扫视 `git diff` 内容，确保未残留临时调试打印（`console.log / print / debugger`）或大段注释掉的废弃代码。

### 2.2 原子化提交与提交信息规范（Commit Convention）
- **单一职责提交（Atomic Commit）**：不同性质的改动（如：新功能开发、独立 Bug 修复、纯代码格式化/移动）应拆分为独立的原子提交，避免将不相关的大量文件混杂在同一个 Commit 中导致后续难以回滚。
- **提交信息格式**：采用精炼的中文 Conventional Commits 标准，单行标题控制在 50 字以内，直指**「改了什么 + 解决什么问题」**：
  - 格式：`<type>(<可选 scope>): <精炼中文摘要>`
  - 标准类型（`type`）：
    - `feat`：新增业务功能或交互特性
    - `fix`：修复缺陷或异常行为
    - `refactor`：不改变外部行为的代码结构重构
    - `style`：纯 UI 样式微调或代码格式修正
    - `docs`：文档、注释或交接快照（`README / docs / HANDOFF`）更新
    - `chore`：构建脚本、依赖配置或工程杂项调整
- **禁止空洞描述**：严禁使用 `update`、`fix bug`、`修改代码`、`wip` 等无信息量的提交说明。

### 2.3 冲突处理与高危操作红线
- **合并冲突消解**：遇到冲突（Conflict）时，必须同时读取冲突文件的当前分支改动（`HEAD`）、传入分支改动及双方的提交意图（`git log`），给出明确的保留/融合方案请用户确认，严禁盲目丢弃任一方代码。
- **破坏性命令禁令**：非经用户点名要求并二次确认，严禁执行 `git push --force`、`git reset --hard`、`git clean -fd` 等不可逆抹除未保存工作区数据的命令。

## 3. 执行流程与门禁（Workflow & Gates）

### Step 1：只读盘点与变更分类
1. 执行 `git status --short` 与 `git diff --stat`（含 staged 与 unstaged），全面掌握当前工作区状态。
2. 识别并剔除不应入库的临时文件或敏感文件，将有效改动按业务逻辑归组。

### Step 2：提交方案拟定与授权门禁（Gate）
- **控制门禁（Gate）**：
  1. 若用户仅说“看下改动”或未明确下达提交指令：输出变更盘点摘要与拟定的 Commit 方案后立即停止。
  2. 若用户已明确下达“提交代码”指令：先通过 2.1 防污染核验，若发现敏感信息或脏文件混入，必须暂停并向用户报告；若全部干净且边界单一，按规范精准指定文件路径执行 `git add <files>` 与 `git commit`。

## 4. 输出格式规范（Output Schema）

变更盘点或提交完成后，统一按以下结构汇报：

### 1. 工作区变更盘点
- **有效变更组**：按模块或提交批次列出 `文件路径 -> 变更类型(M/A/D) -> 改动内容简述`。
- **已排除/需忽略项（如有）**：列出未纳入提交的 `temp/`、本地配置或疑似调试残留文件。

### 2. 推荐提交方案（或已执行 Commit 回执）
- 给出拟定（或已执行）的精确提交信息与包含的文件列表：
  ```text
  feat(module): 精炼描述本次核心变更
  - 包含文件: src/xxx.ts, src/yyy.tsx
  ```

### 3. 后续动作确认
- 明确说明当前是否已提交本地仓库、是否存在未处理冲突，以及是否需要进一步执行其他操作。

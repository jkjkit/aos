# Prompt — 结构化提示词与技能工程规范

## 1. 核心设计原则

- **契约优先于人设**：决定输出质量的并非宽泛的身份修饰（如“资深专家”），而是明确的**输入定义、行为边界、判定标准与输出结构**。
- **正反双向界定**：除陈述期望行为外，必须针对高频偏差明确列出**禁止项（Anti-Patterns）**，通过边界约束消除模型自由发散。
- **高信息密度与正交性**：每条规则只约束一个维度且互不重叠；删除任意一句若不改变模型输出行为，则视为冗余文本并予以剔除。

## 2. 前置分析门禁（编写前必查）

在编写或重构任何 Prompt / Skill 前，先明确以下 3 项基准（若上下文缺失且影响设计走向，先向用户提出 1~3 个收敛问题）：
1. **运行宿主与调用频次**：属于单次对话指令、程序内嵌 System Prompt（API），还是可复用的 Agent 技能文件（`SKILL.md`）？
2. **输入特征**：实际运行时的输入是结构化数据、非结构化长文本，还是简短模糊的自然语言指令？
3. **主要失效模式（Failure Modes）**：未加约束时最易出现的 3 类偏差是什么（如：事实编造、过度执行、格式偏离、冗余铺垫）？后续所有规则均围绕防范这些失效模式展开。

## 3. 标准五段式结构

编写业务 Prompt 或全局 `SKILL.md` 时，按以下 5 个标准模块组织（轻量指令可合并为 3 段，完整 Skill 须涵盖核心模块）：

### 模块 A：目标与边界（Goal & Non-Goals）
- **核心目标（Goal）**：用单句明确定义唯一核心交付物。
- **非目标（Non-Goals）**：明确划定职责外行为，以及在何种情况下应中止或转交其他技能处理。

### 模块 B：判定准则与负向约束（Rules & Constraints）
- 规则表述须具备**可验证性**（能客观判定输出结果是否合规，避免使用“适当”“合理”“尽量”等模糊副词）。
- **标准表述结构**：`[适用条件] -> [执行动作]（禁止：[典型偏差行为]）`
  - ❌ 模糊表述：`请确保输出内容精炼且逻辑清晰。`
  - ✅ 明确表述：`单条结论不超过 2 句话；多方案对比统一采用表格呈现；当输入条件存在逻辑矛盾时，立即中止生成并指出矛盾点。`

### 模块 C：执行流程与门禁（Workflow & Gates）
- 将复杂任务拆解为单向递进的步骤序列（Step 1 $\rightarrow$ Step 2 $\rightarrow$ Step 3）。
- 明确标注**控制门禁（Gate）**：指明哪一步完成后必须暂停以等待外部确认，或满足何种前置条件方可进入下一阶段。

### 模块 D：输出格式规范（Output Schema）
- 提供零歧义的输出结构定义（Markdown 模板、JSON Schema 或字段级约束）。
- **异常与缺省处理**：明确规定当输入信息不足、检索无结果或触发边界条件时的标准输出格式，防止模型自行猜测补全。

### 模块 E：基准示例（Few-Shot Examples，按需配置）
- 仅在输出格式高度严格或文字风格难以仅凭规则描述时，提供 **1 组最小化正反对比示例**（`不合规示例` vs `合规示例`），示例本身须保持精简。

## 4. 交付质量核验清单

Prompt 编写完成后，须通过以下 4 项核验方可交付：
1. **冗余消减核验**：是否已剔除所有无约束力的修饰语、客套用语及空洞形容词？
2. **量化明确性核验**：是否存在未定义判定标准的模糊词汇？如有，是否已替换为具体阈值或显式条件？
3. **规则一致性核验**：不同条款之间是否存在隐性冲突（如同时要求“全面详尽”与“极致简短”）？如有，是否已明确优先级？
4. **边界输入完备性核验**：面对空输入、错误前提或超范围请求时，是否定义了明确的降级或阻断响应？

## 5. 标准交付格式

响应 Prompt 编写或优化请求时，统一按以下结构输出：
1. **设计要点 / 问题诊断**（不超过 3 条，简述核心约束逻辑或原指令的缺陷）
2. **成品指令源码**（置于独立 Markdown 代码块中，便于直接复制或落盘）
3. **边界验证建议**（提供 1~2 个用于检验该指令极限表现的测试输入场景）

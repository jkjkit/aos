# Code Review Workflow

代码审查的标准工作流程。

---

## 适用场景

- Pull Request 审查
- 代码合并前检查
- 定期代码质量审查

---

## 工作流程

```
提交 Pull Request
    ↓
Step 1: 自动化检查
    ↓
Step 2: 审查准备
    ↓
Step 3: 代码审查（review skill）
    ↓
Step 4: 讨论和修改
    ↓
Step 5: 最终审查
    ↓
Step 6: 合并代码
    ↓
Step 7: 验证和监控
```

---

## 详细步骤

### Step 1: 自动化检查

**自动运行：**
- 代码格式检查（Linter）
- 单元测试
- 集成测试
- 代码覆盖率
- 安全扫描

**通过条件：**
- [ ] 所有测试通过
- [ ] 代码覆盖率达标（≥ 80%）
- [ ] 无 Linter 错误
- [ ] 无安全漏洞

---

### Step 2: 审查准备

**审查者检查：**
- [ ] 阅读 PR 描述
- [ ] 理解变更目的
- [ ] 查看关联的 Issue
- [ ] 了解上下文

**提交者准备：**
- [ ] PR 描述清晰
- [ ] 提交历史干净
- [ ] 添加了测试
- [ ] 更新了文档

---

### Step 3: 代码审查

**使用 Skill:** review

**审查维度：**

#### 1. 功能正确性
- [ ] 功能符合需求
- [ ] 边界条件处理
- [ ] 错误处理完整
- [ ] 逻辑正确

#### 2. 代码质量
- [ ] 代码清晰易读
- [ ] 命名规范
- [ ] 复杂度合理
- [ ] 避免重复代码

#### 3. 设计和架构
- [ ] 设计合理
- [ ] 符合现有架构
- [ ] 职责清晰
- [ ] 易于维护

#### 4. 安全性
- [ ] 输入验证
- [ ] 认证授权
- [ ] 敏感数据处理
- [ ] 防止常见漏洞

#### 5. 性能
- [ ] 无明显性能问题
- [ ] 查询优化
- [ ] 内存使用合理
- [ ] 避免 N+1 问题

#### 6. 测试
- [ ] 测试覆盖充分
- [ ] 测试有意义
- [ ] 边界情况测试
- [ ] 错误场景测试

---

### Step 4: 讨论和修改

**反馈方式：**
- 留下具体的评论
- 说明问题和原因
- 提供改进建议
- 保持建设性

**修改流程：**
1. 作者回应评论
2. 修改代码
3. 推送更新
4. 通知审查者

---

### Step 5: 最终审查

**确认：**
- [ ] 所有评论已解决
- [ ] 修改符合预期
- [ ] 再次运行测试
- [ ] 批准 PR

---

### Step 6: 合并代码

**合并策略：**

- **Squash and Merge**: 压缩成一个提交（推荐）
- **Merge Commit**: 保留所有提交历史
- **Rebase and Merge**: 线性历史

**合并前检查：**
- [ ] 所有审查者批准
- [ ] CI/CD 通过
- [ ] 无冲突
- [ ] 分支最新

---

### Step 7: 验证和监控

**部署后：**
- [ ] 功能正常工作
- [ ] 无新增错误
- [ ] 性能稳定
- [ ] 监控指标正常

---

## 审查标准

### Approve（批准）

代码满足以下条件：
- 功能正确
- 代码质量好
- 测试充分
- 无明显问题

### Request Changes（请求修改）

代码存在问题需要修改：
- 功能有 bug
- 设计不合理
- 安全隐患
- 缺少测试

### Comment（评论）

提供建议但不阻塞合并：
- 可选的优化
- 未来改进建议
- 知识分享

---

## 评论指南

### 好的评论

✅ **具体明确**
```
❌ 不好：这里有问题
✅ 好的：这里应该检查 null，否则会抛异常
```

✅ **提供原因**
```
❌ 不好：改用 const
✅ 好的：这个变量不会被重新赋值，建议用 const 提高可读性
```

✅ **提供建议**
```
❌ 不好：性能不好
✅ 好的：这里有 N+1 查询问题，建议使用 includes 预加载
```

✅ **保持友好**
```
❌ 不好：这代码写得太烂了
✅ 好的：这段代码可以简化，建议提取成独立函数
```

## 常见问题

### 问题 1: 代码风格问题

**解决方案：** 使用自动化工具（Prettier, ESLint）

### 问题 2: 大型 PR 难以审查

**解决方案：** 
- 拆分成小的 PR
- 每个 PR 专注一个功能
- 建议 < 400 行代码

### 问题 3: 审查拖延

**解决方案：**
- 设置审查时间限制（< 24 小时）
- 轮换审查责任
- 使用审查提醒

### 问题 4: 意见不一致

**解决方案：**
- 线上或线下讨论
- 团队制定编码规范
- 技术负责人最终决定

## 审查清单

### 提交者清单

- [ ] PR 描述清晰
- [ ] 关联了 Issue
- [ ] 添加了测试
- [ ] 更新了文档
- [ ] 自我审查过代码
- [ ] 运行了所有测试
- [ ] 解决了所有冲突

### 审查者清单

- [ ] 理解了变更目的
- [ ] 审查了代码逻辑
- [ ] 检查了测试覆盖
- [ ] 验证了安全性
- [ ] 考虑了性能
- [ ] 留下了建设性反馈
- [ ] 及时响应（< 24 小时）

---

## 最佳实践

### 1. 快速响应

审查请求后 24 小时内完成

### 2. 小而频繁

小的 PR 更容易审查，建议 < 400 行

### 3. 建设性反馈

关注代码，不批评人

### 4. 知识分享

通过审查学习和教学

### 5. 标准一致

团队统一审查标准

# Bug Fix Workflow

修复 Bug 的标准工作流程。

---

## 适用场景

- 生产环境发现 Bug
- 测试中发现缺陷
- 用户报告问题

---

## 工作流程

```
接收 Bug 报告
    ↓
Step 1: 确认和重现（debug skill）
    ↓
Step 2: 分析根因（debug skill）
    ↓
Step 3: 修复实现（coding skill）
    ↓
Step 4: 代码审查（review skill）
    ↓
Step 5: 测试验证
    ↓
Step 6: 提交代码（git skill）
    ↓
Step 7: 部署发布
    ↓
Step 8: 验证和监控
```

---

## 详细步骤

### Step 1: 确认和重现

**使用 Skill:** debug

**输入:**
- Bug 报告
- 错误信息
- 环境信息

**输出:**
- 重现步骤
- 环境配置

**检查点:**
- [ ] Bug 可以稳定重现
- [ ] 收集了完整的错误信息
- [ ] 确认了影响范围

---

### Step 2: 分析根因

**使用 Skill:** debug

**输入:**
- 重现步骤
- 相关代码
- 错误日志

**输出:**
- 根本原因
- 影响分析

**检查点:**
- [ ] 定位到具体代码
- [ ] 理解了问题原因
- [ ] 评估了影响范围

---

### Step 3: 修复实现

**使用 Skill:** coding

**输入:**
- 根因分析
- 修复方案

**输出:**
- 修复代码
- 测试代码

**检查点:**
- [ ] 修复了根本原因
- [ ] 添加了测试
- [ ] 代码符合规范

---

### Step 4: 代码审查

**使用 Skill:** review

**输入:**
- 修复代码
- 上下文信息

**输出:**
- 审查意见
- 改进建议

**检查点:**
- [ ] 修复合理
- [ ] 没有引入新问题
- [ ] 测试充分

---

### Step 5: 测试验证

**测试类型:**
- 单元测试
- 集成测试
- 回归测试
- 手动测试

**检查点:**
- [ ] 所有测试通过
- [ ] Bug 已修复
- [ ] 没有回归

---

### Step 6: 提交代码

**使用 Skill:** git

**Commit Message 格式:**
```
fix(scope): brief description

Fixes #issue-number

- What was the problem
- How it was fixed
- What was tested
```

**检查点:**
- [ ] Commit message 清晰
- [ ] 关联了 Issue
- [ ] 创建了 Pull Request

---

### Step 7: 部署发布

**部署策略:**
- 紧急 Bug：直接发布 hotfix
- 一般 Bug：随下次发布

**检查点:**
- [ ] 部署到测试环境
- [ ] 部署到生产环境
- [ ] 更新了版本号

---

### Step 8: 验证和监控

**验证:**
- 生产环境测试
- 监控错误日志
- 用户反馈

**检查点:**
- [ ] Bug 不再出现
- [ ] 系统运行正常
- [ ] 用户满意

---

## 优先级指南

### Critical（严重）
- 影响：系统崩溃、数据丢失
- 响应：立即修复
- 时间：< 4 小时

### High（高）
- 影响：核心功能不可用
- 响应：当天修复
- 时间：< 1 天

### Medium（中）
- 影响：部分功能受影响
- 响应：本周修复
- 时间：< 1 周

### Low（低）
- 影响：小问题、优化
- 响应：计划修复
- 时间：下次发布

---

## 最佳实践

### 1. 快速响应

严重 Bug 要立即响应，不要拖延

### 2. 根因分析

不要只修复表面问题，找到根本原因

### 3. 完整测试

确保修复有效且没有副作用

### 4. 清晰沟通

及时更新 Bug 状态，通知相关人员

### 5. 文档记录

记录问题和解决方案，避免重复

---

## Hotfix 流程

紧急修复的特殊流程：

```
发现严重 Bug
    ↓
从 main 创建 hotfix 分支
    ↓
快速修复和测试
    ↓
合并到 main 和 develop
    ↓
立即发布
    ↓
监控验证
```

# Coding

## 目标

把明确的需求转化为能通过项目正常入口使用的代码变更。实现应符合现有项目结构、命名、技术选型和调用约定，并保持相关功能的正确性与可维护性。

## 适用场景

- 开发新功能和接口
- 修复错误和回归问题
- 调整已有逻辑或配置
- 重构代码结构
- 编写或补充必要的测试
- 排查构建、运行和集成问题

## 工作方式

### 理解需求和项目

先确认用户目标、影响范围和验收结果。查找项目说明、需求文档、技术文档、目录结构、配置文件和相关实现，了解功能的正常入口。

检查调用方、数据结构、错误处理和已有测试。修改已有代码前识别其被哪些功能使用，保留调用方依赖的行为。

需求缺少细节时，基于现有项目约定建立最小假设。只有无法判断实现方向或验收标准时才提出问题。

### 设计实现

先确定职责、输入、输出、状态变化和失败路径，再开始修改代码。优先复用已有类、方法、数据表示和工具，避免引入重复逻辑。

根据业务复杂度拆分模块。保持边界清晰、职责集中和依赖方向容易理解，避免为尚未发生的需求提前引入复杂抽象。

处理完整的支持范围，包括旧数据、空值、非法输入、重复操作、并发执行、重试和中途失败。操作可能部分完成时，保证结果状态一致。

### 编写代码

遵循项目已有的语言、框架、格式化、命名和错误处理约定。变量名、函数名和模块名应直接表达其用途。

代码保持易读。使用简单的控制流和适度的辅助函数，避免压缩写法、隐藏分支、无意义的封装和过度复用。

注释只说明代码用途、特殊原因、约束或不容易从实现中看出的决策。注释应当与代码保持同步。

涉及用户界面时，结合 `uiux` Skill 关注信息层级、交互状态、响应式布局、可访问性和设计 Token。

### 保持兼容

默认保留现有调用方依赖的接口、数据格式、错误语义和生命周期。需要改变既有行为时，明确识别受影响的入口并同步处理相关代码。

兼容旧数据和历史状态。迁移、回填或版本转换应当可重复执行，并在失败或重试时保持状态一致。

### 验证结果

实现完成后运行项目已有的格式检查、类型检查、单元测试、集成测试、构建或启动命令。优先使用项目文档和配置中定义的验证方式。

根据变更范围检查正常路径、边界输入、错误路径和相关旧功能。涉及前端时检查主要设备尺寸、加载状态、空状态、错误状态和关键交互。

发现失败时分析根因并修复，再重新验证。不要通过跳过检查、隐藏错误或修改无关配置来掩盖问题。

## 变更原则

- 只修改完成任务所需的文件和逻辑
- 保留用户已有修改和未涉及功能
- 不引入未使用的依赖、配置或辅助代码
- 不为满足测试而改变正确的业务行为
- 不进行与任务无关的格式化和重命名
- 不使用会丢弃用户修改的命令处理不确定状态

## 交付标准

完成编码任务后说明：

- 实现了什么功能或修复了什么问题
- 修改涉及哪些主要文件或模块
- 运行了哪些验证命令及其结果
- 哪些行为、假设或边界需要用户确认
- 是否存在尚未解决的问题

如果无法完成某项验证，明确说明缺失的环境、命令或外部依赖，以及已经完成的替代检查。

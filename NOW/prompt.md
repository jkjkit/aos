# Prompt Writing

## 目标

把用户对任务的描述转化为模型可以稳定执行的提示词。提示词需要表达任务目的、行为方式和结果要求，并根据使用场景控制复杂度。

## 输入

用户可能提供完整需求，也可能只提供一句用途。至少需要理解以下内容中的一项：

- 提示词要解决的问题
- 模型需要完成的任务
- 期望得到的结果

如果用户只提供用途，根据用途推导必要结构。只有缺少的信息会影响任务方向时，才提出问题。

## 写作方法

先理解提示词要解决的问题，再确定模型需要扮演的身份、完成的任务和交付的结果。

### 确定任务

明确模型要做什么、服务谁、结果用于什么场景。将模糊目标改写成具体动作，例如分析、提取、比较、生成、修改、审查或执行。

### 组织结构

根据任务需要选择以下内容：

- `role` 用于定义身份、专业范围和工作视角
- `purpose` 用于说明任务目的和成功结果
- `context` 用于提供必要背景和判断依据
- `instructions` 用于说明执行方式、重点和处理顺序
- `input` 用于承载用户输入、变量或外部资料
- `output` 用于规定格式、语言、风格、长度和内容范围
- `examples` 用于展示文字难以准确说明的行为或格式
- `uncertainty` 用于规定信息不足、冲突或无法判断时的处理方式

这些内容按任务取舍，不要求全部出现。

### 编写指令

使用直接、具体、可执行的表达。明确告诉模型要完成的动作和交付的结果。

规则较复杂时，说明规则的目的或适用条件，帮助模型处理未被示例覆盖的情况。

优先描述期望模型采取的行为。限制性要求应当与任务直接相关，并说明需要避免的问题。

### 使用结构化标记

提示词同时包含身份、背景、指令、资料、示例和输出要求时，使用语义明确的 XML 标签进行分层。标签名称应直接表达内容含义，并保持同一提示词中的命名一致。

简单任务使用自然语言即可，避免为了形式增加无意义的标签。

### 使用示例

当目标格式、语气或判断方式难以通过规则表达时加入示例。示例应与任务一致，覆盖典型情况和重要边界，不能包含与要求冲突的行为。

### 处理不确定性

允许模型说明信息不足、无法判断或存在多个合理答案的情况。要求模型区分事实、推断和假设，避免为了完成格式而编造内容。

## 输出要求

默认输出一份可以直接使用的完整提示词。提示词前可以简要说明采用的结构和关键假设。

如果用户要求优化已有提示词，保留原意和有效要求，只调整影响清晰度、执行稳定性和输出质量的部分。

如果用户要求创建系统提示词，重点定义长期行为、能力边界和输出风格。具体任务资料和一次性输入放入任务提示词或输入区块。

如果用户没有指定模型，使用通用写法。只有模型特性会影响结构时，才加入模型相关写法。

## 模板

以下模板是结构参考。用途是最小必需信息，其他区块根据任务需要保留、调整或删除。

```text
<role>
你是{{角色或专业身份}}。
</role>

<purpose>
你的任务是{{说明任务目的和期望结果}}。
</purpose>

<context>
{{提供影响判断或表达方式的必要背景}}
</context>

<instructions>
请{{说明要完成的动作、执行重点和必要步骤}}。
</instructions>

<input>
{{用户提供的内容、变量或外部资料}}
</input>

<output>
请按照{{格式、语言、风格、长度或内容范围}}输出结果。
</output>

<examples>
{{仅在示例有助于表达要求时加入输入和输出示例}}
</examples>

<uncertainty>
信息不足或无法可靠判断时，请说明不确定之处和需要补充的信息，不要编造事实。
</uncertainty>
```

## 最终检查

完成提示词后检查：

- 任务目标是否明确
- 指令是否能够直接执行
- 输入和输出是否对应
- 结构是否与任务复杂度匹配
- 是否加入了用户没有要求的规则
- 信息不足时是否有合理处理方式

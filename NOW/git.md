# Git Workflow

## 目标

通过清晰、可回溯的 Git 操作管理项目变更。每次操作都应明确当前状态、变更范围和下一步影响。

## 适用场景

- 查看仓库状态、分支和提交历史
- 分析工作区和暂存区变更
- 整理、暂存和提交修改
- 编写简明清晰的提交信息
- 检查提交前的代码和文档状态
- 处理分支、合并和冲突
- 生成变更摘要或交接信息

## 工作方式

### 先观察状态

开始 Git 操作前，查看仓库根目录、当前分支、工作区状态、未跟踪文件和最近提交。结合当前任务判断哪些变化属于本次工作。

检查文件内容和差异，识别用户已有的修改。保留无法确认归属的变化，并在必要时说明它们影响了哪些操作。

### 控制变更范围

只处理用户要求或当前任务明确涉及的文件。暂存时按文件或逻辑变更选择内容，避免把无关修改、临时文件或敏感信息加入提交。

提交前确认 `.gitignore`、环境文件、密钥、构建产物和临时文件没有被误加入。

### 审查变更

提交前查看完整 diff，并从以下角度检查：

- 功能是否完成，行为是否符合任务目标
- 是否存在明显错误、遗漏或不必要的修改
- 代码、配置、测试和文档是否保持一致
- 是否混入格式化、重命名或其他无关变更
- 是否包含敏感信息、调试代码或临时内容

发现问题时先修复，再继续提交流程。变更未达到可提交状态时，明确说明原因和剩余工作。

### 验证后提交

根据项目已有命令运行必要的检查、测试、构建或类型检查。优先使用项目文档、配置和脚本中定义的命令。

验证完成后重新查看状态和 diff，确认验证过程没有产生未预期的文件或修改。

提交信息应简洁说明变更目的和主要内容。一个提交尽量对应一个清晰的逻辑变更，避免把不相关的工作混在同一提交中。

### 处理分支和合并

创建或切换分支前确认当前工作区状态，避免影响未提交修改。

合并、变基或解决冲突前说明操作范围。冲突解决后逐个检查冲突文件，确认保留的逻辑正确，再运行验证并提交结果。

涉及远程分支、推送、强制更新或删除分支时，先确认目标和影响。远程操作需要用户明确要求。

## 安全边界

不使用 `reset --hard`、`checkout --`、批量删除或其他会丢弃修改的操作处理不确定状态。需要清理或回退时，先确认目标文件、影响范围和用户意图。

不覆盖、撤销或删除用户未创建的修改。发现工作区存在其他人的变化时，将其视为需要保留的项目状态。

不提交密钥、令牌、个人配置、生成文件或未经确认的大型文件。发现疑似敏感内容时暂停提交并说明具体文件。

## 提交标准

完成 Git 操作后说明：

- 当前分支和仓库状态
- 本次处理的变更范围
- 执行过的审查和验证
- 提交编号与提交信息
- 尚未处理或需要用户决定的事项

如果只是查看或分析 Git 状态，输出发现和建议动作，不自动创建提交。

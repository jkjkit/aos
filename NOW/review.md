# Review

## 目标

通过检查变更内容、相关上下文和验证结果，发现会影响正确性、安全性、兼容性、可维护性或用户体验的问题。

审查应帮助作者做出修复决策，重点输出真实、具体、可定位的问题，避免把个人偏好当作缺陷。

## 适用场景

- 审查工作区、暂存区或提交中的代码变更
- 检查功能实现、接口、数据处理和配置调整
- 审查测试覆盖、错误处理和兼容性
- 检查前端界面、交互状态和响应式实现
- 检查文档、脚本、迁移和部署变更
- 提交前进行整体质量检查

## 工作方式

### 确定审查范围

先查看项目状态、变更列表、完整 diff 和相关提交。明确本次审查的目标、基线、影响模块和已有验证结果。

阅读变更涉及的调用方、数据结构、配置和测试，不只根据 diff 的局部内容下结论。

保留用户已有修改，不在审查过程中擅自重写、回退或清理文件。用户明确要求修复时，再结合 `coding` Skill 执行修改。

### 理解预期行为

根据需求文档、任务描述、现有实现和测试确定正确行为。区分明确要求、项目约定和个人推断。

如果预期行为无法确认，说明依据和不确定性，不把猜测直接报告为缺陷。

### 检查关键问题

优先检查以下方面：

- 功能逻辑是否覆盖正常路径、边界输入和失败路径
- 输入校验、权限控制、敏感数据和外部数据处理是否安全
- 状态变化、事务、重试、并发和部分失败是否可能产生不一致
- 接口、数据格式、旧数据和调用方是否保持兼容
- 错误是否被正确处理、记录和传递
- 测试是否覆盖变更的主要行为和高风险路径
- 配置、脚本、迁移和文档是否与实现一致
- 前端的信息层级、交互反馈、响应式和可访问性是否完整
- 是否引入了无必要的复杂度、重复逻辑或明显性能问题

结合变更风险安排审查重点，不机械地逐项检查无关内容。

### 验证发现

对疑似问题追踪到具体代码路径、输入条件或运行状态。必要时读取相关文件、运行最小复现、执行已有测试或检查配置，确认问题确实存在。

只有能说明触发条件、实际影响和修复方向时，才将内容作为正式发现输出。

## 问题分级

按照对用户、数据、系统和交付的影响排序：

- `阻断` 会导致核心功能无法使用、数据损坏、严重安全问题或提交无法交付
- `严重` 会在常见场景下造成明显错误、兼容性破坏或重要功能失效
- `一般` 会影响部分场景、错误恢复、可维护性或用户体验
- `轻微` 主要是低风险改进，不影响主要功能

分级基于实际影响和发生条件，不根据修改代码的大小判断。

## 输出格式

每条问题包含：

1. 严重程度
2. 文件路径和行号
3. 具体问题
4. 触发条件或证据
5. 建议的修复方向

按严重程度从高到低排列。问题描述直接说明行为、影响和原因，让作者可以定位并处理。

审查结果没有可确认的问题时，明确说明未发现问题，并列出实际执行过的检查和仍未覆盖的范围。

将非阻断性的观察、疑问和风格建议单独列出，避免它们掩盖真实缺陷。

## 审查标准

- 结论应基于变更和项目上下文
- 每个问题应能被独立定位和复现
- 不重复报告同一个根因造成的多个表现
- 不把格式偏好、重构意愿或未证实风险当作缺陷
- 优先报告影响用户、数据、系统稳定性和交付的内容
- 审查完成后给出验证范围和剩余不确定性
